01 · Cost of inaction

如果不做会怎么样

核心问题是设计规范与前端实现之间存在脱节：设计侧难以确认规则是否真实落地，开发侧缺少统一、可复用的实现约束。进入真实产品环境后，多站点并行建设会进一步放大这种脱节；同时设计侧受资源和推动边界限制，难以单独完成跨站点治理。

Core purpose 统一设计与开发规范
如果不做

设计规范与前端实现持续脱节：设计侧无法确认规则是否真实落地，开发侧缺少统一的组件与实现约束，二次解释、设计走查和返工持续发生；多个站点会进一步放大这一问题。

AI foundation 构建 AI 生成基础
如果不做

缺少结构化 Tokens、组件契约、页面模式和验证规则，AI 只能自由生成或依赖预置模板与数据填充，难以稳定产出符合规范的页面。

Prototype 更快完成原型
如果不做

每个页面继续重复搭建组件和基础交互，原型效率与完成度更多依赖个人经验，难以形成可复用的制作能力。

Responsive 真实多端表现
如果不做

交互、动效和响应式规则仍停留在静态交付和文字说明中，需要前端重新理解、实现，再通过设计走查发现偏差。

Handoff 减少设计转译成本
如果不做

设计稿、组件说明和前端实现继续分离，沟通、标注、二次实现与返工会持续发生，设计和开发难以共享同一事实来源。

03 · Potential users

谁会使用，谁来协作

这套代码组件库不强制要求设计师使用。是否采用，应根据具体任务、个人能力和协作方式判断：适合用代码快速制作或验证的场景可以采用；更适合在 Figma 中探索，或直接由前端实现的场景，可以继续使用原有方式。角色参与因事而异、因人而异，按需协作即可。

按场景使用

设计师与产品经理

使用规范、组件和页面模式快速制作高保真原型，明确页面目标、用户任务和内容范围。

待验证：产品经理是否直接操作，或主要提供 Brief
按需协作

前端开发

复用 React 组件、Design Tokens、类型和交互实现，并验证原型代码进入业务项目的真实成本。

涉及公共资产时

设计系统维护者

维护 Tokens、公共组件、设计规则、Storybook 文档以及自动化质量门槛。

需要业务确认时

业务 Stakeholder

04 · Short-term goal

短期希望解决什么？

短期不同时承诺统一所有前端代码、自动发布或替代 Figma。当前只验证原型效率和设计到开发交付是否得到改善。

目标 A

提升原型制作效率与完成度

  • 更快完成符合 YAMI 设计标准的高保真页面。
  • 直接呈现真实交互、动效和响应式行为。
  • 减少重复定义颜色、间距、组件状态和多端规则。
目标 B

改善设计到开发的交付链路

  • 减少前端重新理解设计稿和重复实现交互的时间。
  • 减少设计走查、返工和沟通轮次。
  • 让修改意见能指向组件、Token、内容或页面组合。

05 · Long-term direction

长期期望解决什么？

长期方向是让设计规范、组件、原型和前端实现逐步使用同一套可执行资产。但“统一前端代码”只有在真实业务项目采用并形成版本机制后才能成立。

01 · Token

统一视觉规则来源

以 Design Tokens 表达颜色、字体、间距和响应式等视觉规则，减少多处维护。

02 · Component

使用真实组件制作原型

让 Storybook 组件同时服务于设计确认、原型制作和前端实现。

03 · Delivery

建立可执行的设计交付

通过自动 QA 检查设计规范、运行时、视觉和可访问性，再进入人工确认。

04 · Adoption

验证业务前端直接复用

通过真实项目接入验证组件包、版本升级和维护成本，决定是否能够形成统一代码资产。

当前表述

项目有机会提高设计原型与前端实现的一致性，并逐步验证组件代码能否直接复用；现阶段不宣称已经实现设计与业务前端代码统一。

06 · How to start

从 Brief 到真实原型

当前操作链路仍以代码和 AI Agent 为主。下一阶段需要专门验证设计师与产品经理能否独立完成，并补充面向非开发用户的操作说明。

01 · Brief

明确页面目标与范围

写清楚用户任务、核心内容、业务限制和目标设备，避免只描述视觉样式。

02 · Reference

查看规范和现有组件

在 Storybook 中查看组件状态、使用规则、页面模式以及桌面和移动端表现。

03 · Generate

使用 AI 辅助制作 React 原型

根据设计规范、组件目录和已有页面 Recipe 生成或修改页面，不重新发明已有组件。

04 · Verify

检查真实交互与多端表现

在 Storybook 中检查交互、动效、桌面端、移动端以及关键状态。

05 · Refine

进行定向修改

将反馈落实到组件 Props、Design Tokens、内容或页面组合，然后重新验证。

07 · Figma boundary

不是替代，而是阶段分工

当前不以全面替代 Figma 为目标。Figma 继续承担自由探索和评议，代码组件库聚焦标准化、高保真和接近实现的阶段。

探索阶段 Figma

适合自由探索、视觉发散、快速布局、设计评议和非代码协作。

  • 快速尝试不同方向
  • 低成本讨论视觉与布局
  • 支持广泛的设计协作
收敛阶段 代码组件库

适合使用既有规范和真实组件，完成响应式、可交互、接近实现的高保真原型。

  • 复用标准组件和页面模式
  • 直接表达交互与多端行为
  • 减少标注和二次实现
优先验证

是否能够减少标准组件重复拼装、多端稿件维护、手工标注，以及前端重新实现交互原型的工作量。

08 · Collaboration & review

协作方式暂不定案

当前优先研究设计到开发的完整链路。可以将“分布式制作、集中式治理”和三层 Review 作为验证假设，而不是已经落地的组织机制。

01

自动 QA

检查组件规范、类型、运行时、交互、响应式、视觉和可访问性。

  • 减少基础规范错误
  • 保留可重复验证结果
02

设计与产品 Review

检查视觉表现、组件使用、用户流程、内容和业务目标。

  • 反馈指向具体责任字段
  • 避免模糊的“感觉不对”
03

工程与发布 Review

检查代码质量、组件复用、性能、接入成本及公共资产变更。

  • 原型确认与代码合并分离
  • 正式发布独立确认

09 · Next validation

下一步不是扩功能，而是补证据

选择一个边界明确的真实页面，从 Brief、原型、Review 到前端接入完整走一遍，用事实决定是否继续投入和采用哪种协作模式。

优先 完成一个端到端案例

记录设计、生成、修改、Review 和前端接入全过程，找到真实阻塞点。

量化 建立前后对比指标

比较原型耗时、开发耗时、返工轮次、规范问题和最终完成度。

决策 确定角色与 Review

根据真实案例明确谁制作、谁维护、谁审核，以及哪些代码能够直接复用。

项目判断标准

如果真实案例能稳定减少制作时间、沟通与返工，同时保持设计质量和前端可维护性，这个方向值得继续；否则需要收窄场景或调整链路。

10 · Decision

是否继续推进？

当前证据支持继续验证，但还不足以支持全面推广。建议以一个真实业务页面为范围推进下一阶段，并在完成后作正式决策。

建议决策
有条件推进下一阶段验证

推进的是端到端真实案例，不是组件库的全面推广，也不承诺立即统一所有前端代码或替代 Figma。

  • 完成一个从 Brief、原型、Review 到前端接入的真实页面。
  • 记录制作耗时、开发耗时、返工轮次、规范问题和维护成本。
  • 若效率、质量与可维护性同时改善，则继续投入；否则收窄场景或停止推进。
