00 · Overview

这份指南如何帮助你

Storybook 是 YAMI 真实组件、页面模式和使用规则的共同入口。你不需要先理解代码，也可以查找组件、体验状态、检查多端表现，并用准确链接与团队协作。

找到

从 Foundations、Assets、Components 和 Pages 中找到正确参考。

理解

查看组件用途、变体、状态、内容规则、响应式和无障碍要求。

组合

先选择最接近的完整页面，再把目标拆成可以复用的页面模块。

验证

切换语言、主题和屏幕尺寸，完成交互、视觉和内容 Review。

正确定位

Storybook 负责查看、理解和验证；新的页面组合通常由现有页面模式配合 Codex、Kiro 或工程协作者完成。

01 · Why Storybook

为什么不只看静态设计稿

静态设计稿可以表达方向，但 Storybook 可以直接展示组件在真实浏览器里的行为、状态和多端变化。

需要确认静态设计稿Storybook
组件状态需要逐张补充或文字说明直接体验 Hover、Focus、Loading、Disabled 等状态
响应式依赖多个画板和标注切换真实宽度，查看布局和内容变化
中英文容易只完成其中一个版本在同一页面切换并检查表达与长度
交互需要原型连线或口头解释直接操作真实组件和页面
协作反馈容易停留在截图位置链接可以绑定具体组件、状态和页面
不是二选一

Figma 继续适合自由探索、视觉发散和早期评议；Storybook 更适合在方向收敛后确认真实组件、交互和实现边界。

02 · Library map

Storybook 里有什么

从左侧导航开始。先判断你需要的是设计规则、品牌资产、单个组件，还是一个可参考的完整页面。

Foundations

设计基础

颜色、字体、布局、圆角和响应式规则。适合确认“应该长什么样”。

Primitives

底层变量

尺寸、颜色和字体的基础值。主要用于进阶规范检查，不是普通搭页的起点。

Assets

品牌资产

Logo、图标等可复用资源。用于选择正确版本并确认颜色、尺寸和背景要求。

Components

组件

Button、Header、Product Card、Product List 等真实组件及其状态和用法。

Pages

完整页面

首页、专题页、搜索页和商品详情页等。搭建新页面时应优先从这里找参考。

Recommended

先页面，后组件

如果目标是搭页面，先找到最接近的 Page，再回到 Components 确认模块细节。

03 · Interface

Storybook 界面怎么使用

完成一次有效检查，通常只需要认识左侧导航、Story、Docs、Controls，以及顶部的语言、主题和屏幕尺寸切换。

01 · Navigate

找到 Story

在左侧按 Foundations、Assets、Components 或 Pages 展开并选择目标。

02 · Inspect

看 Story 与 Docs

Story 用于操作真实界面；Docs 用于查看说明、主示例、Controls 和其他 Stories。

03 · Adjust

切换环境

用工具栏切换中文/English、Light/Dark，以及 360–1920px 的预设尺寸。

04 · Share

分享准确状态

保留具体 Story、语言、主题、尺寸和问题描述，避免只发 Storybook 首页。

Controls 的边界

Controls 只用于临时预览参数变化，不会自动保存一个新组件或页面版本。

04 · Read a component

如何读懂一个组件

不要从代码属性开始。先回答它解决什么问题，再确认内容、状态、响应式和使用边界。

维度需要回答常见位置
Purpose它解决什么问题？什么时候使用或避免使用？Docs / Usage
Anatomy由哪些内容区域组成？哪些是必需的？Primary Story / Usage
Variants有哪些样式、尺寸和层级？Controls / Showcase
States默认、Hover、Focus、Loading、Disabled 如何表现？Stories
Content文案、数字、图片和图标有哪些限制？Usage
Responsive移动端和桌面端是否改变结构、尺寸或交互？Viewport
Locale & Theme中英文和 Light/Dark 是否都完整？Toolbar
Accessibility键盘、焦点、标签和触控区域是否正确？a11y / Usage
Do / Don’t常见误用是什么？是否已有可复用示例？Usage / Stories
不要把视觉相似当作可以替换

例如链接和按钮可能看起来相似，但承担不同语义。最终选择需要同时符合用户任务、交互和无障碍要求。

  2. 判断复用、扩展或新建
  3. 定义内容、状态与交互契约
  4. 补齐 Story、Usage 与验证

输出组件契约、Story、使用说明和验证结果

创建组件提示词

请为 YAMI Design System 处理【组件需求】。

使用场景：
【用户任务与业务场景】

开始前：
1. 检查 Storybook、generated/catalog.json 和相近组件。
2. 判断应该复用、扩展还是新建。
3. 如果已有组件可以满足，请停止新建并说明复用方案。

如果需要创建或扩展：
- 使用 YAMI 语义 Token，并保持 Design System 包边界。
- 定义组件用途、内容、状态、响应式、交互和无障碍要求。
- 补充 meta.json、usage.md、Stories 和公共 export。
- 覆盖必要状态、中文 / English、Light / Dark 与关键屏幕尺寸。
- 运行生成检查和 pnpm validate。

只修改直接相关文件。完成后提供 Storybook 入口、验证结果和未解决问题。

07 · Review

页面 Review 清单

Review 不只看“像不像设计稿”。需要同时确认目标、结构、内容、状态、响应式、交互和可访问性。

  • 页面目标和核心用户任务是否清楚
  • 信息层级和 CTA 优先级是否正确
  • 是否优先复用已有组件
  • 正常、加载、空、错误和禁用状态是否覆盖
  • 文案长度是否适配容器
  • 中英文是否表达一致且自然
  • 图片比例、焦点和裁切是否正确
  • 360、375、768、1024、1440 等关键宽度是否完整
  • Light/Dark 是否保持可读性
  • Hover、Focus、点击和键盘操作是否正确
  • 动效是否用于说明状态变化
  • Reduced Motion 是否仍能完成任务
  • 是否出现自定义颜色、圆角或影子
  • 问题是否能指向具体组件、内容或页面模块
Review 结果必须可复现

记录具体 Story、语言、主题、屏幕尺寸、操作步骤和预期结果。不要只写“页面感觉不对”。

09 · Boundary & practice

能力边界与首次练习

Storybook 是共同参考和验证入口，不是拖拽式页面编辑器，也不负责接入业务数据或发布生产页面。

可以直接完成

在 Storybook 中

  • 浏览组件和页面
  • 查看文档和 Controls
  • 切换语言、主题和屏幕尺寸
  • 操作组件与页面
  • 分享精确链接并 Review
需要协作

在 Storybook 之外

  • 保存新的组件或页面组合
  • 创建全新交互和公共能力
  • 接入真实业务数据
  • 合并代码与版本发布
  • 正式生产上线

00 · Creator overview

什么时候进入知识库

当你需要保存新的组件、页面组合、页面版本或公共规则时，使用本 Tab。目标不是教所有人写代码，而是让任务、边界、输入和验收足够清楚。

Extend扩展现有组件

已有组件用途正确，但缺少一个稳定状态、尺寸或内容能力。

Create新建组件

多个页面都会复用、已有组件无法合理承担的新公共能力。

Version新建页面版本

页面类型不变，但内容、模块组合或布局方向需要独立 Review。

Maintain维护规则与发布

涉及 Token、动效、公共组件契约、生成文件或包版本。

Codex 与 Kiro 的关系

两者使用同一套 YAMI 规则、任务输入和验收标准。知识库只描述平台入口差异，不维护两套互相漂移的创建流程。

01 · Architecture

系统由哪些层组成

公共视觉规则、组件、页面组合、Storybook 和 Canvas 各有明确责任。新能力应放在最小且正确的拥有层。

DTCG Design Tokens颜色、字体、间距、圆角、响应式等源规则
@yami/design-system公共 React 组件、Assets、Usage、Metadata 与规则验证
@yami/prototypes使用公共组件组合页面、Fixture 与 Page Stories
Storybook查看、文档、Controls、交互和 a11y 验证
Canvas方向导入、页面工作台和预览
Business Frontend业务数据接入、工程集成、发布和生产维护
外部 Agent，不是运行时模型

Codex/Kiro 在仓库外部或 IDE 中生成和修改受规则约束的资产；Storybook 和 Canvas 不应被描述为在浏览器中秘密调用模型。

02 · Dependencies

框架与依赖边界

不要把某一应用层的技术栈带入公共组件包。依赖选择首先服从层级责任，而不是个人偏好。

层级当前主要技术负责边界
Design SystemReact、Base UI、CSS Modules、DTCG公共规则与组件不导入 Next.js、Motion、Zod 或 Canvas Runtime
PrototypesReact、Design System、Contracts页面组合与 Fixture不重复实现已有基础组件
StorybookStorybook、React-Vite、ViteDocs、Controls、a11y、测试不承担真实业务数据和生产发布
CanvasNext.js、Motion、Contracts页面工作台和方向预览不得反向侵入公共组件包
QualityTypeScript、Vitest、Playwright、ESLint类型、交互、视觉与规则检查不能以截图或 HTTP 200 替代完整验证
框架版本如何维护

版本号从各层 package.json 核对，不在本说明中复制一份长期维护的版本清单。

03 · Source of truth

事实从哪里来

知识库负责解释和导航，不复制完整规则。每类事实只保留一个权威来源。

Design设计规则

DESIGN.md 是完整规范；DESIGN.compact.md 是面向设计师和 PM 的快速入口。

Token视觉变量

tokens/**/*.tokens.json 是源；generated/ 是确定性生成结果，不手工改值。

Component组件契约

meta.json、usage.md、Story 和公共 export 共同定义可维护组件。

Page页面模式

packages/prototypes/pages/ 保存页面实现、Fixture、Types 和 Stories。

AgentCodex/Kiro 规则

packages/design-system/SKILL.md 定义复用顺序、边界和最低验证。

Release版本与历史

Changesets、Git 和受保护的合并记录负责版本与发布事实。

04 · Foundations

设计、内容与动效规范

创建组件或页面时，必须同时处理视觉、响应式、内容和动效。不能只做到桌面端默认状态。

Visual视觉
  • 品牌红只用于 Logo
  • 操作红用于 CTA、促销和错误
  • 最多四层文字层级
  • 使用语义 Token 和五类圆角
  • 卡片默认无边框和重阴影
Responsive响应式
  • 从移动端开始验证
  • 检查 360、375、768、1024、1440
  • 处理文字换行与图片焦点
  • 触控区域满足 44–48px
  • 不假设桌面缩小就是移动端
Content内容
  • 中英文语义平等
  • CTA 直接、行动导向
  • 不引入无证据的商品表达
  • 测试真实长度，不只写占位符
  • 产品 UI 中不使用 Emoji
Motion动效
  • 功能优先，不做装饰动效
  • CSS transition 是组件默认选择
  • 不动画宽高、字体和网格位置
  • 状态变化必须可被打断
  • 支持 prefers-reduced-motion
Motion 的层级边界

Canvas 可以使用 motion；公共 Design System 包当前禁止导入 Motion。需要声明式复杂动效时，先判断它是否真的属于公共组件层。

05 · Decision tree

创建前先判断

很多“新组件”其实只是新的内容、Story 或页面组合。先选择最小拥有层，可以减少重复和维护成本。

  1. 已有组件能完成吗？ 能 → 直接复用，优先通过 Props、内容或组合解决。
  2. 只需要不同内容或状态吗？ 是 → 新建 Fixture 或 Story，不复制组件。
  3. 已有组件用途正确，但缺少稳定能力吗？ 是 → 扩展现有组件和契约。
  4. 新能力会被多个页面复用吗？ 是 → 评估为新的公共组件。
  5. 只服务一个页面吗？ 是 → 先放在页面内部，不提前抽象。
  6. 用户目标或信息架构发生改变吗？ 是 → 创建新页面类型，而不是伪装成一个 Story。
创建申请必须回答

已检查哪些组件、为什么不能复用、谁会重复使用、需要哪些状态和屏幕、谁负责维护、如何验证。

07 · Version model

页面与版本模型

在创建之前先说明“版本”具体指什么。不是每一个 Story 都是独立页面版本。

类型含义推荐实现示例
Story Variation同一实现的不同预览状态Story Args / GlobalsLoading、Empty、Mobile
Content Version结构不变，只更换文案、商品或图片新 Fixture同一专题页的不同主题内容
Layout Version页面类型不变，但模块组合或顺序变化共享页面实现 + 独立版本输入商品列表页的不同筛选结构
Page Type用户目标或信息架构发生实质变化新页面实现与 StorySearch Results 与 Product Detail
Component Version公共组件契约发生变化更新组件、Metadata 和 StoriesButton 新增稳定 Form
Package Version包能力对外变化ChangesetDesign System minor release
当前原则

只换数据，不复制页面实现；布局变化但页面类型不变，优先共享实现；新模块会被多个页面复用时，先建设公共组件。

09 · Quality gates

质量检查分四层

自动测试和真实浏览器验证各自证明不同事实。缺少其中一层时，需要明确报告未验证边界。

01 · Source

源文件检查

  • 改动是否属于正确层
  • 是否复用 Catalog 组件
  • 是否使用真实 Token
  • 是否保留包边界
02 · Automated

自动检查

  • Generated artifacts
  • TypeScript / Lint
  • Unit / Storybook tests
  • Design principles / a11y
03 · Runtime

真实浏览器

  • 监听进程与正确工作区
  • DOM 和关键交互
  • 语言、主题、Viewport
  • Console 与页面错误
04 · Human

人工体验 Review

  • 用户任务和信息层级
  • 视觉与内容质量
  • 业务准确性
  • 是否可以进入开发

最低验证命令

pnpm generate
pnpm test:storybook
pnpm validate
git diff --check
不能偷换证明

Build 成功、HTTP 200 或干净的 Git 状态都不能单独证明页面视觉、交互和多端表现已经正确。

10 · Release & troubleshoot

版本、发布与故障处理

原型确认、代码 Review、合并和生产发布是不同状态。交付说明必须准确描述当前完成到哪一步。

状态含义可以如何描述
Draft正在生成或尚未完成验证初稿，可继续 Review
In Review已有可运行结果，等待设计/产品/工程确认已提交 Review，尚未合并
Validated已完成约定检查和真实 Storybook 验证已验证，可进入发布流程
Stable公共能力已合并并按约定发布已发布，提供版本和合并证明
Deprecated不再推荐使用，但仍可能保留兼容已废弃，提供替代方案

找不到合适组件

先检查 Pages 和相近复合组件，再进入创建前判断树；不要直接新建视觉相似组件。

Controls 修改没有保存

Controls 是预览。需要保存时创建 Fixture、Story 或页面版本，并进入代码 Review。

Storybook 启动失败

检查依赖、端口和监听进程所属工作区；不要终止其他会话的 Storybook。

Generated files 漂移

运行 pnpm generate，检查生成差异是否由本次源文件改动导致，再重新验证。

测试通过但页面不对

回到真实 Storybook 检查 DOM、计算样式、交互、Console 和目标 Viewport。

Codex/Kiro 改动太大

缩小允许文件范围，明确“只改直接相关文件”，要求先诊断复用边界再实施。

发布边界

未经明确授权，不自动提交、推送、合并或部署。需要发布时，单独确认改动范围、检查、版本和目标环境。
