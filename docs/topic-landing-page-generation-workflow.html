YAMI · Generation System

Topic Landing Page
生成工作流

将主题关键词、模板路由、商品选择、组件配置、英文内容、图片生产和质量验收收束为一条可追溯、可重跑的 AI 生成链。

Workflow version v0.2

基线：ANUA English Topic Landing Page

更新：2026-08-11

Core automation flow

从关键词到发布

前期由系统自动完成模板路由、选品、组件配置、页面生成与 QA；用户只在最后 Review，确认后发布。

  1. 01
    INPUT 输入关键词

    输入品牌型、商品型或活动型主题词。

  2. 02
    ROUTE 识别主题并匹配模板

    AI 解析实体与意图，生成 ThemeIntent 并匹配预设模板。

    ↳ 3 个模板 品牌型 · 商品型（商品 / 品类 / 成分）· 活动型（节日 / 场景 / 活动）
  3. 03
    SELECT 构建双层商品池

    先建立精准主题 PrimaryPool，再从核心商品扩展 RelatedPool。

    ↳ 两个逻辑池 PrimaryPool：精准主题商品 · RelatedPool：搭配 complementary / 相似 substitute
  4. 04
    CONFIG 配置组件与商品

    根据模板与可支撑场景生成组件清单，并按商品池边界分配商品和内容资产。

    ◇ 品牌组件条件 品牌主题隐藏；非品牌主题自动增加品牌组件。
  5. 05
    GENERATE 生成完整页面

    生成英文文案、图片和页面数据，并按照模板确定性装配页面。

  6. 06
    VERIFY 自动 QA

    验证数据、视觉、运行时和可访问性，输出结构化检查结果。

    ↺ 未通过：返回配置 只重跑失败组件，再次生成并验证，不重做整页。
  7. 07
    REVIEW 用户 Review

    查看完整页面与 QA 结果，确认内容、选品和视觉表现。

    ↺ 需要调整：局部返回 将意见映射到对应组件，调整后重新进入生成与 QA。
  8. 08
    PUBLISH 确认并发布

    用户确认后发布，并保存版本、来源证据与回滚记录。

01 · Input

输入关键词，生成基础 Brief

用户只输入一个主题关键词。系统保存原始输入，并自动写入固定的美国市场、英文环境和允许来源，生成供下一步 AI 语义理解使用的 GenerationBrief。

01

接收主题关键词

保留用户原始输入用于审计、复现和回溯；空值与长度检查可在进入 AI 前拦截无法解析、意外粘贴或超出输入约束的请求，避免无效调用。主题类型需结合语义和证据判断，因此交给下一步 AI 理解，避免仅凭字面规则过早误判。

  • 输入 theme_keyword
  • 类型由下一步 AI 判断
02

生成 GenerationBrief

写入固定市场、英文 locale、允许来源、run_id 和 brief_hash，作为 AI 理解主题词的输入。

  • status = intent_pending
  • 相同输入可追溯

GenerationBrief 输出示例

{
  "run_id": "topic-20260811-001",
  "theme_keyword": "ANUA",
  "brief_hash": "sha256:...",
  "market": "us",
  "locale": "en-US",
  "source_scope": ["yami_catalog", "product_detail", "brand_official"],
  "status": "intent_pending"
}

06.2 · Evidence policy

先定义什么是真的

自动化质量取决于来源和时效，而不是提示词长度。动态字段必须在运行时刷新；静态品牌信息也必须保存原文、来源和内容哈希。

数据域 主来源 允许回退 默认时效 AI 权限
SKU、商品名、规格 YAMI 商品详情页 / 商品接口 品牌页商品卡 本次运行快照 只标准化，不改写事实
价格、库存、折扣 当前市场实时目录 无；过期即阻塞 默认 30 分钟，可配置 禁止推断或补齐
品牌定位与功效 品牌官方资料＋YAMI 品牌页 商品详情中的一致描述 内容哈希变化时刷新 可归纳，不得新增主张
Product Type 与任务 商品名称、形态、用法和现有类目 规则库与已批准历史映射 规则版本变化时重算 可分类，低置信度转人工
评论 对应商品的真实用户评论 无可靠评论则不生成模块 保存抓取时间与评论 ID 禁止编造；只允许截短
包装与商品图 YAMI / 品牌官方原始图片 已批准的本地资产版本 图片哈希变化时复审 可合成背景，不可重绘身份
field_is_usable = source_allowed ∧ observed_at_within_ttl ∧ identity_resolved ∧ conflict_count = 0

置信度不能覆盖来源缺失。即使模型“很确定”，没有允许的来源或存在冲突时，字段状态仍为 blocked。

02 · Route

AI 理解主题词并匹配模板

AI 先结合关键词与目录语境识别实体、购物意图和场景，再归入品牌型、商品型或活动型，输出可解释的 ThemeIntent，最后选择 3 个预设模板之一。

01

品牌型模板

关键词能够唯一解析到品牌实体时使用；突出品牌定位、核心系列与品牌商品，不额外生成品牌组件。

02

商品型模板

关键词指向商品集合、一级类目或成分功效时使用；以商品发现为主，并自动增加品牌组件。

03

活动型模板

关键词表达时间、使用场景或营销活动时使用；强化主题叙事与跨品牌选品，并自动增加品牌组件。

识别信号 匹配模板 品牌组件 示例关键词
唯一品牌实体，品牌商品覆盖充分 品牌型 隐藏，避免重复表达品牌 ANUA、SKIN1004
商品名、品类词或成分实体命中 商品型 显示，解释候选品牌来源 Heartleaf Toner、Sunscreens、Niacinamide
节日词、季节词、场景或活动实体命中 活动型 显示，承接多品牌内容 Summer Skincare、Back to School
多个类型同时命中或置信度不足 商品型回退 显示，并记录 route_reason 模糊主题词或新兴趋势词

AI 语义理解与模板路由

brief_ready接收 GenerationBrief

读取主题关键词与系统固定的市场、语言和允许来源。

intent_interpretedAI 理解主题词

识别品牌、商品、品类、成分、节日或场景实体，并推断购物意图。

type_classified判断三类主题

归入 brand、product 或 activity，保存置信度与判断依据。

intent_ready生成 ThemeIntent

输出 theme_type、entity_type、entity、intent、confidence 和 matched_signals。

template_matched匹配预设模板

根据 ThemeIntent 选择模板和组件清单，并应用品牌组件规则。

selection_ready进入自动选品

保存 route_reason，无需人工确认，继续构建 PrimaryPool 与 RelatedPool。

ThemeIntent 与路由证据

每次匹配必须保存 theme_type、entity_type、entity、intent、confidence、matched_signals、template_id、template_version 和 route_reason。后续 Review 若要求换模板，系统从选品步骤重新运行，而不是在生成后的页面上直接改结构。

页面模块主题 Hero

04.1 · ThemeHero module

主题 Hero ThemeHero

ThemeHero 把主题证据压缩成一个可验证的主题命题：一句主标题、一段说明、三组短标签和一张真实商品主视觉。AI 负责提炼与装配，不重绘包装，也不补写没有来源的功效。

Input 主题证据

主题关键词、ThemeIntent、模板类型、商品证据、市场语言、合法功效表述和来源时间。

Decision 主题命题

选择可被商品证据支持、能覆盖主题意图且适合日常购物语境的一条叙事。

Asset 主视觉

真实商品合照、可选氛围背景、固有尺寸、替代文本和预采样背景色。

Output ThemeHero

英文标题、两行说明、英文标签、图片资产和可选 CTA 的受类型约束 Props。

01

内容生成

主标题只表达一个主题命题；说明补充适用场景与护理范围；标签控制为三组英文短语。描述超过两行时使用“More / Less”交互。

02

图片策略

主图必须能识别真实商品并保留包装比例，输出 src、alt、width、height；氛围图可复用或单独提供。backgroundColor 来自主图底部区域预采样，用于首帧文字对比与移动端遮罩。

03

响应式装配

桌面端为文案与商品图双栏，移动端为全宽背景图叠加内容，并依据背景明暗选择黑字或白字。CTA 只有在存在明确目标时生成；当前基线主动隐藏两枚 CTA。

QA 审核门

标题与功效必须能回指来源；英文标签顺序和商品身份与 Spec 一致；图片固有尺寸必须预留布局空间；移动端首屏需通过文字对比、两行截断、展开状态、窄屏横向溢出和 reduced-motion 检查。

页面模块精选分类

04.2 · ShortcutRail module

精选分类 ShortcutRail

它不是品牌全量目录，而是帮助用户快速进入购物意图的一级入口。每个入口由一个稳定的 Product Type、一组候选商品和一张圆形缩略图组成。

Input PrimaryPool

精准符合主题的商品、名称、当前分类、可售状态、商品图和来源链接。

Decision 一级归类

按核心使用目的和护肤步骤归类；每个商品只有一个主分类。

Asset 7 张图

600×600 WebP，真实商品主体，适配圆形 full-bleed 裁切。

Output ShortcutRail

英文名称、稳定顺序、目标链接和本地图片资源。

01

分类决策

固定输出清洁与去角质、爽肤水与棉片、精华与护理、乳液与面霜、防晒、面膜、彩妆七个一级 Product Type。按核心用途归类，每个 SKU 只保留一个主分类。

02

商品与图片

每类选择 1–2 个身份清晰、当前可售且外形有代表性的商品构图；导出 600×600 WebP，圆形 full-bleed 裁切后仍完整识别主体，不加入价格、折扣或 UI 徽标。

03

输出与联动

七个稳定 value 同时驱动英文标签、图片文件和 #explore-more-{value} 锚点。点击入口需选中“Explore More”同名 Tab 并滚动到对应商品池。

QA 审核门

必须恰好输出 7 个唯一 ID，英文标签顺序与 Product Type 顺序一致；图片与代表商品可追溯；移动端标签最多两行且英文单词不拆分；逐个点击验证锚点、选中状态和对应商品列表，不允许死链或错 Tab。

页面模块从这里开始

04.3 · ThemeProductList module

从这里开始 ThemeProductList

该模块不是再次按品类陈列商品，而是把品牌商品组织成五个护理任务。每个任务同时切换场景图、主题文案和六个商品，让用户从“我要解决什么”进入购买路径。

Input 需求证据

产品功效、使用步骤、适用场景、可售状态、商品图片和品牌叙事边界。

Decision 5 个任务

温和清洁、舒缓调理、淡斑提亮、补水修护与日间防护。

Asset 5 张场景图

每个任务一张真实商品场景图，并记录 alt、来源与下方文案区域的背景色。

Output ThemeProductList

5 组 themes；每组包含 value、英文标签、场景内容和 6 个商品。

01

任务生成

任务按护肤流程和用户目标生成：Cleanse & Reset、Calm & Prep、Brighten & Correct、Hydrate & Repair、Protect & Finish。名称描述行动，不夸大结果。

02

商品分配

每组固定 6 个可售商品，按“核心步骤优先、辅助步骤补齐”排序。商品可跨任务复用，但必须在每个任务中承担不同且可解释的护理角色，同组内不得重复 SKU。

03

场景与文案

场景图必须对应当前任务中的真实商品；标题说明使用场景，描述解释步骤。预采样 backgroundColor 保证图片未完成采样前也能选择可读前景色，图片和商品卡均保留目标链接。

QA 审核门

验证 5 个稳定主题值及每组 6 个唯一商品；切换 Tab 时场景、英文标题、描述和商品必须原子更新；逐组检查 SKU 与任务相关性、图片身份、证据边界、价格时效、桌面横向翻页和移动端横向滚动。

页面模块热门精选

04.4 · ProductList rail module

热门精选 ProductList Rail

热门精选回答“第一次来先买什么”。当前基线按 ANUA 品牌页“销量由高到低”的 All 快照保留前 8 个商品，并用本地图片保证 Storybook 可重复验证。

Input 销量快照

排序后的品牌页商品、SKU、价格、可售状态、商品链接、抓取时间和来源链接。

Decision 前 8 个

保持源页销量顺序，不用主观“代表性”覆盖真实排名。

Asset 8 张本地图

从源商品图固化的确定性资源，与英文商品数据共用同一商品身份。

Output ProductList

rail 布局、商品卡、分类标签、前后翻页和加入购物车回调。

01

排名与时效

只在同一 observed_at 快照中排序；缺货、身份冲突或链接失效的商品进入审核，不静默换位。标题可本地化，SKU、排名、价格和源链接必须保持可追溯。

02

Tab 商品边界

UI 展示 All 加七个 Product Type，并通过 productsByTab 从 PrimaryPool 输出对应商品。分类结果不足时少展示，不从 RelatedPool 补满。

03

商品与图片

使用真实商品主图、品牌链接和商品链接；本地资源名称与稳定商品 ID 对齐。商品卡不展示生成式功效、虚构评分或来源中不存在的促销徽标。

QA 审核门

校验 All 恰好 8 个商品、顺序与销量快照一致、各分类 productsByTab 只含对应 Product Type；检查链接语言、价格来源和图片身份，并验证切换后商品列表、选中状态与滚动位置同步。

页面模块品牌（非必须）

04.5 · BrandSpotlight module

品牌（非必须） BrandSpotlight

品牌组件只服务非品牌主题：当主题为商品型或活动型时，它用可追溯证据解释代表品牌及关联商品；品牌型主题默认隐藏，避免与 ThemeHero 重复。

Input 候选品牌

ThemeIntent、PrimaryPool 中的品牌覆盖、品牌资料、可售商品、来源链接和观察时间。

Decision 展示条件

仅在 theme_type 为 product 或 activity，且存在证据充分的代表品牌时生成。

Asset 品牌视觉

已批准的品牌标识或品牌图、替代文本、固有尺寸与可访问目标链接。

Output BrandSpotlight

品牌名称、证据化简介、代表商品、图片资产、链接和显示状态。

01

条件生成

品牌型主题必须隐藏；商品型或活动型主题才进入候选判断。没有明确代表品牌时允许省略，不用低置信度结果填满模板。

02

品牌选择

按主题相关性、商品覆盖率、当前可售状态和证据完整度排序；保存 brand_id、confidence、matched_signals 和 selection_reason。

03

内容与商品

简介只能压缩已批准品牌资料，不生成无来源主张；代表商品必须来自同一品牌并与当前主题相关，品牌入口和商品链接均可访问。

QA 审核门

验证非品牌主题条件、brand_id 唯一性、品牌资料来源、图片身份与商品归属；品牌型主题中不得渲染该组件，缺少合格候选时应输出 hidden，而不是强制生成。

页面模块顾客怎么说

04.6 · ReviewList module

顾客怎么说 ReviewList

评论模块只编排可追溯的真实体验证据。AI 可以做主题覆盖、排序和受控翻译，但不得生成评论、增强功效结论或把评论绑定到另一个商品。

Input 评论证据

原始评论、评分、匿名用户、商品 SKU、商品图、来源链接和抓取时间。

Decision 3 条体验

覆盖清洁、舒缓补水与淡斑提亮，并避免三条评论表达同一主题。

Asset 商品缩略图

每条评论绑定对应商品图、替代文本、品牌名、商品名和目标链接。

Output ReviewList

稳定 ID、五分制评分、评论正文、匿名用户和关联商品。

01

真实性优先

评论正文与评分必须来自同一条源记录；受控翻译需保留原文和 source_ref，不改变态度、肤质、使用周期或功效强度。没有评论证据时宁可隐藏模块。

02

商品绑定

稳定 review_id 同时关联 product_id、图片、品牌、商品名和 href；评分允许半星。评论中的产品体验与底部商品卡必须指向同一 SKU。

03

隐私与本地化

仅展示已匿名化用户名，不推断身份。英文模块标题固定为“What Customers Say”；长评论在卡片中受控截断，但数据层保留完整文本。

QA 审核门

03.1 · Two-layer product pools

自动选品与双层商品池

系统先根据 ThemeIntent 建立精准主题核心池，再用核心商品派生搭配与相似关系。主题场景必须由真实商品覆盖支撑，不能先生成场景再用弱相关商品补满。

01

读取意图与可售全集

读取 ThemeIntent 和同一 catalog snapshot，按市场、可售状态、商品身份与来源完整度执行硬过滤。

  • 输入主题实体、购物意图和模板约束
  • 输出可参与评分的 eligible_products
02

构建 PrimaryPool

只保留精准符合主题词和 ThemeIntent 的商品，保存 relevance_score、matched_signals 与 selection_reason。

  • 核心组件只从该池取商品
  • 不足时减少展示或进入 QA，不由弱相关商品补位
03

生成可支撑主题场景

根据 PrimaryPool 的功能、使用步骤和商品覆盖生成场景；覆盖不足的场景自动合并、降级或删除。

  • 场景必须引用真实商品证据
  • 不为凑模板容量凭空生成使用路径
04

派生 RelatedPool

以 PrimaryPool 商品为锚点扩展关联商品，并严格区分搭配购买与相似替代两种关系。

  • complementary：补充步骤或完成完整 Routine
  • substitute：同功能、价位或品牌替代
05

按组件分配并 QA

先锁定 pool_scope，再按组件目标重新排序；验证锚点、关系理由、重复策略和商品覆盖。

  • 搭配购买使用 complementary；相似商品单独保留

03.3 · Pool scoring and fallback

双层商品池的排序与回退

两个商品池来自同一商品快照，但拥有不同准入规则。组件选品必须先确定 pool_scope，再在池内按组件目标排序；RelatedPool 不能静默填补 PrimaryPool 的数量缺口。

1

核心池边界

Theme Hero、精选分类、从这里开始、热门精选、品牌组件及探索更多的 All / 分类 Tab 只使用 PrimaryPool。核心池不足时减少展示或进入 QA。

2

关联关系可追溯

RelatedPool 每个商品必须保存 relation_type、anchor_product_ids、relation_reason 和 confidence；complementary 与 substitute 不得混为同一列表。

3

组件内再次精排

锁定商品池后，再按场景相关性、销量、可售状态、素材质量和缩略图识别度排序；跨组件允许有意重复，同一列表不得重复 SKU。

primary_score = 0.45 × theme_fit + 0.20 × availability + 0.15 × evidence_quality + 0.10 × popularity + 0.10 × asset_quality related_score = 0.40 × relation_strength + 0.20 × anchor_coverage + 0.20 × availability + 0.10 × diversity + 0.10 × asset_quality

硬过滤先于评分。PrimaryPool 不满足主题相关性即淘汰；RelatedPool 没有明确锚点和关系理由即淘汰，不能靠总分覆盖。

精选分类图片的代表商品数量

分类规模 图片主体数 默认策略 回退方式
1–2 个有效商品 1 选择最具代表性的单品，放大商品轮廓。 缺图则标记阻塞，不生成虚构商品。
3–8 个有效商品 1–2 主商品＋形态互补的次商品。 两个包装过于相似时退回单品。
9 个以上 2 用两种主要形态覆盖分类，不做商品墙。 按销量和素材质量选择替补。

05.3 · Image production

三种图片生成模式

目标生产模式是“真实商品抠图＋模板背景”，它能兼顾品牌准确性与批量一致性。参考图生成适合快速原型，但必须增加包装文字检查。

Fastest

A · 原商品图裁切

直接使用商品卡主图，统一尺寸和圆形裁切。速度最快、商品最真实，但背景和视觉语言不一致。

Production target

B · 抠图＋模板合成

保留真实包装像素，自动移除背景，再放入版本化的品牌场景模板。适合稳定批量生产。

Current prototype

C · 参考图生成

以商品图作为身份参考，让模型统一背景与构图。视觉自由度高，但可能改写包装细节。

任务：生成 {brand} 的 {category_zh} / {category_en} 分类缩略图。

身份约束：
- 只使用已选择的真实商品参考图：{selected_product_ids}
- 保持商品包装形状、主色、开合方式与品牌识别
- 不新增商品、Logo、标题、价格、折扣、评分或 UI

统一视觉：
- 1:1 正方形，适配圆形 full-bleed 裁切
- 商品位于中心安全区，主体 1–2 个
- 浅色韩系棚拍，柔和自然阴影
- 使用 {category_visual_cue} 表达分类，不遮挡包装

输出：
- 600 × 600 WebP
- 文件名：category-{category_slug}.webp
- 记录 prompt_version、source_images、output_hash

ThemeHero

  • 场景商品允许出现在热门精选或探索更多，因为模块意图不同；但不得让多个场景拥有完全相同的商品集合。

05.2 · English content

只生成一份英文内容

Stable 实体 ID

Frozen 商业事实

内容英文生成规则必须保留验证方式
品牌与系列名称使用官方英文名称，不自行翻译或改写商标。大小写、数字和系列符号品牌术语表匹配
商品名称保留品牌、系列、核心成分、品类和规格，仅规范英文语序。浓度、单位、容量、套装数量字段级 token 对比
营销与场景文案基于证据生成简洁自然的英文表达，不扩写未经证实的功效。证据边界与使用顺序evidence_ref 完整性
评论只显示英文原文评论；无可靠英文评论时隐藏模块。原始文本、作者、评分、商品review_id 回溯
可访问性文本根据真实商品和场景生成英文 alt 与 ARIA label。商品身份和交互目的语义与可访问性检查
输出边界

生成结果只包含 locale = en-US。中文仅用于这份流程文档的说明，不进入 PageSpec、组件 Props 或发布页面。

06.1 · Automated QA

自动 QA：通过后才进入 Review

系统自动检查来源、策略、数据、资产、运行时、视觉和可访问性。全部通过才生成 Review Package；失败项只回到对应组件重跑，不重做整页。

01
来源与时效

每个事实字段有允许的 source_ref；价格、库存和排序未超过 TTL。

02
分类完整性

所有有效商品有唯一一级分类；未分类、冲突和低置信度商品显式列出。

03
模块策略

每个模块符合容量、排序、重复和回退规则；模块之间表达不同购物意图。

04
英文内容完整

标题、说明、标签、商品名、alt 与 ARIA 文案均为 en-US，且事实字段和 evidence_ref 完整。

05
商品真实性

名称、图片、价格、库存和评论均可回溯；无模型生成的虚构 SKU 或功效。

06
资产规范

图片存在、尺寸正确、可加载、无 UI 残留，包装身份和文字未被错误重绘。

07
运行时与交互

Schema、类型、Storybook、锚点、Tab、横向滚动和加载更多行为通过。

08
视觉与可访问性

桌面 / 移动裁切、文本行数、对比度、键盘、ARIA、reduced motion 和无布局跳动通过。

Current · Spec v0.2

定义完整的 AI 编排、证据策略、模块规则、英文内容契约和发布边界。

  • 现有 fixture 作为 ANUA 基线
  • 前期生成与 QA 全自动
  • 用户仅在最终 Review 确认
Next · Runner v0.3

实现读取 CatalogSnapshot、输出 PageGenerationSpec 的可重跑命令行 Runner。

  • 来源采集与快照缓存
  • 规则化分类和模块规划
  • 生成 fixture / asset manifest
Later · Connected v1.0

接入实时目录、审核台和发布系统，把已批准 Spec 编译成可发布页面。

  • 模块级差异和定向重跑
  • 快照版本与一键回滚
  • 用户 Review 通过后发布

07 · User review

最终 Review 是唯一人工确认门

系统把完整英文页面、自动 QA 结果、来源证据和本次变更一起提交给用户。用户只做最终确认或提出定向修改，不参与前期模板、选品和组件配置。

Preview 完整页面

桌面与移动端真实渲染，包含全部组件、商品、英文内容和图片。

QA 检查报告

展示通过项、自动修复记录、剩余风险和组件级验证证据。

Trace 来源回溯

商品、文案、评论和图片都能回到对应 source_ref 与 observed_at。

Diff 变更范围

标明模板版本、商品集合、组件配置和资产相较上一版本的差异。

01

打开 Review Package

锁定 PageGenerationSpec、QA 报告、预览地址和证据清单。

02

检查完整页面

核对内容、选品、模块顺序、图片、桌面与移动端表现。

03

确认或提出修改

通过则进入发布；修改请求必须指向模板、组件、商品或内容字段。

04

冻结 Review 结果

记录 reviewer、reviewed_at、结论、备注和被批准的 spec_hash。

用户结论系统状态下一步重跑边界
确认approved生成不可变发布包不重跑
需要修改changes_requested返回对应配置并再次自动 QA只重跑受影响组件
拒绝blocked停止发布并保留证据由新 Brief 重新开始
不在成品上直接改

任何修改都映射回模板、组件配置、商品分配、英文内容或图片资产，再从受影响节点生成并自动 QA；页面预览始终是结构化 Spec 的结果。

08 · Publish

确认后发布，并保留回滚证据

发布只接受已通过自动 QA 且用户确认的 spec_hash。系统冻结页面、内容和资产版本，执行构建与烟雾测试，并把部署结果、来源证据和回滚入口写入发布记录。

Gate 发布前提

QA 全部通过，user_review = approved，且审核的 spec_hash 未发生变化。

Package 不可变版本

冻结 PageSpec、en-US 内容、商品快照、资产 manifest 和规则版本。

Deploy 发布与检查

构建发布页面，检查状态码、关键路由、组件渲染和桌面 / 移动端访问。

Record 证据与回滚

保存 release_id、URL、commit、部署时间、验证结果和上一稳定版本。

01

冻结发布包

计算 spec_hash、content_hash 和 asset_manifest_hash，禁止隐式变更。

02

编译页面

由已批准 Spec 装配现有组件，生成可部署的英文主题页。

03

部署与烟雾测试

验证公开 URL、首屏、锚点、商品链接、资源加载和响应式布局。

04

记录或回滚

成功则写入发布记录；失败则回滚上一稳定版本并保留失败证据。

发布硬门

没有已批准的 user_review、Review 后 spec_hash 发生变化、关键烟雾测试失败，任一条件成立都禁止发布。回滚不会覆盖失败记录。
