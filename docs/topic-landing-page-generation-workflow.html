Core automation flow

从关键词到发布

目标流程由系统自动完成模板路由、选品、组件配置、页面生成与 QA；用户只在最后 Review，确认后发布。当前 v0.2 是流程规格与 ANUA Fixture 基线，不代表 Runner、实时目录或发布系统已经接通。

  1. 01
    INPUT 输入关键词并选择站点

    校验关键词与美国站 / 加拿大站，生成可追溯的 GenerationBrief。

  2. 02
    ROUTE 识别主题并匹配模板

    输出 ThemeIntent，以及包含组件契约、槽位与容量规则的 TemplateRoute。

    ↳ 3 个模板 品牌主题 · 商品导购（商品 / 品类 / 领域属性）· 场景活动（节日 / 季节 / 场景 / 活动）
  3. 03
    SELECT 构建双层商品池

    冻结 ProductPools、唯一 Product Type 与可支撑场景，不分配组件 SKU 或生成资产。

    ↳ 两个逻辑池 PrimaryPool：精准主题商品 · RelatedPool：搭配 complementary / 相似 substitute
  4. 04
    CONFIG 配置组件与商品

    决定组件显隐与顺序，按槽位分配最终商品，并输出 PagePlan。

    ◇ 品牌组件条件 品牌主题隐藏；非品牌主题仅在代表品牌证据充分时展示。
  5. 05
    GENERATE 生成内容、图片并装配页面

    实例化 PageGenerationSpec，并生成桌面与移动端 Preview。

  6. 06
    VERIFY 自动 QA

    输出 QAReport；全部通过后生成 ReviewPackage。

    ↺ 未通过：定向修复 返回失败节点所属阶段，最多自动重试两次；仍失败则阻塞进入 Review。
  7. 07
    REVIEW 用户 Review

    确认或提出定向修改，输出不可变的 ReviewDecision。

    ↺ 需要调整：局部返回 将意见映射到模板路由、选品、组件或资产所属阶段，局部重跑后重新 QA。
  8. 08
    PUBLISH 确认并发布

    发布已批准版本，输出 ReleaseRecord 与可回滚记录。

04 · Component configuration

配置页面组件

TemplateRoute 定义组件契约，系统在本阶段决定组件显隐与顺序，并为每个槽位分配最终商品、内容任务和图片任务。七个业务模块共享同一商品快照、分类体系、稳定实体 ID 和页面装配契约。

Input

输入

状态为 selection_ready 的 TemplateRoute，以及状态为 ready 或仅包含模板允许降级项的 ProductPools、ProductTaxonomy、SupportedScenes 与组件槽位、容量和复用规则。selection_blocked 不得进入 04。

Process

处理

实例化模板组件，决定显隐与顺序，按商品池边界把最终商品 ID 分配到具体槽位，并创建英文内容与图片资产任务；品牌主题隐藏品牌组件，非品牌主题仅在代表品牌证据充分时展示。

Output

输出

输出状态为 plan_ready 的 PagePlan，包含组件顺序、显示状态、槽位到商品 ID 的映射、内容与资产任务以及复用策略。可选组件不满足条件时关闭并记录原因；必需组件无法满足时输出 plan_blocked，不进入页面生成。

以下是组件规格，不是连续执行步骤

ThemeHero、ShortcutRail、ThemeProductList、热门精选等条目分别定义各组件的输入、槽位、容量和回退规则；Runner 在同一个 PagePlan 阶段按依赖关系规划它们，不把组件名称当作一条固定的串行流程。

01 · Input

输入关键词并选择销售站点

用户输入一个主题关键词，并明确选择美国站或加拿大站。系统保存原始输入，根据站点配置写入对应的英文 locale、币种、目录来源和可售 / 可配送边界，生成供下一步 AI 语义理解使用的 GenerationBrief。

01

接收并校验关键词与站点

Input

输入

接收用户提交的 raw_keyword 和销售站点 site；站点只允许 us（美国站）或 ca（加拿大站）。

Process

处理

原样保存 raw_keyword，清理首尾空格并检查是否为空、是否超过长度上限；同时校验 site 是否属于允许枚举。本步骤不判断主题类型，也不允许 AI 猜测站点。

示例：ANUA、鱼腥草爽肤水可通过；纯空格会被拦截，大段商品详情会提示缩短。

Output

输出

输出通过校验的 theme_keyword 与 site，并保留 raw_keyword；主题类型留给下一步 AI 结合语义与业务证据识别。

02 · Route

AI 理解主题词并匹配模板

路由采用“AI 判断 + 系统校验”：AI 结合 GenerationBrief 与目录提示，在品牌主题、商品导购和场景活动中三选一；系统再验证实体、来源与可售商品是否满足模板要求，通过后才放行。

主题理解与模板路由主流程

intent_pending 01 输入 · 读取 GenerationBrief

读取 theme_keyword、raw_keyword、site、locale、currency、source_scope、site_config_version、run_id 与 brief_hash，确认本次路由的输入、销售站点和证据边界。

intent_interpreted 02 处理 · AI 理解主题与购物意图

按“主题词 → 实体与修饰条件 → 购物意图 → 检索条件 → 主题类型”解释输入，并形成可验证的 ThemeIntent；本步骤不直接选商品。

route_validating 03 校验与纠错 · 将 AI 判断转为可执行路由
  • 格式检查：确认 ThemeIntent 的必填字段完整，theme_type 仅为 brand、product 或 activity。
  • 证据验证：确认品牌、商品等实体可在允许的数据来源中找到，或节日、场景命中预设规则。
  • 执行条件：通过只读的 CatalogCoverageProbe 确认所选站点有足够的可售 / 可配送候选，并覆盖模板要求的必需类目、有效站点链接和主图；这里只判断模板可行性，不冻结商品池或组件 SKU。
  • 纠错与结果：实体别名、类型冲突或覆盖不足等可修复问题，仅返回失败字段、失败原因和可用证据让 AI 自动重判一次；不得修改 raw_keyword、site、允许来源或模板门槛。通过后进入 selection_ready；重判仍失败则输出 route_blocked 与 blocked_reason，并停止进入选品。
selection_ready 04 输出 · 生成 ThemeIntent 与 TemplateRoute

校验通过时输出 ThemeIntent，以及包含 template_id、template_version、必选 / 可选组件、槽位 Schema、容量规则和品牌组件策略的 TemplateRoute；template_id 只允许 topic-brand、topic-product-guide 或 topic-activity。本阶段不分配具体商品。重判仍失败则输出 route_blocked 与 blocked_reason。

重点：AI 如何理解主题词与购物意图

这一步回答两个问题：关键词在所选站点中指向什么，以及用户希望买什么、解决什么问题、在什么条件下使用。AI 负责语义解释和检索约束生成；站点目录实体、允许来源与商品可售 / 可配送状态由下一步系统校验。

主题词→实体与修饰条件→购物意图→检索条件→主题类型
Input

输入

读取清洗后的 theme_keyword、用户原始输入 raw_keyword、site、locale、currency，以及该站点允许使用的目录词表和数据来源。原始输入用于保留语境，清洗词用于稳定解析和检索。

Process

处理

  1. 识别核心实体与修饰条件

    从主题词中拆出品牌、商品、品类、领域属性、节日或场景实体，以及人群、规格、季节等限定条件；领域属性按目录 Schema 解释，例如美妆的成分与功效、食品的口味与过敏原、家居的材质与尺寸、日用的功能与包装规格。

  2. 理解购物意图

    把关键词补全为可执行的购物目标，重点回答三个维度：

    • 想买什么：某品牌商品、某类商品、具体商品，或一组场景商品。
    • 想解决什么：如护肤需求、饮食偏好、空间收纳、清洁补给或其他购物任务。
    • 在什么条件下使用：如季节、场景、人群、规格、口味、材质、尺寸、过敏原或兼容性限制。
  3. 形成商品检索约束

    生成必须包含或排除的品牌、品类与领域属性，以及用于召回的关键词、别名和同义词。检索约束只定义候选范围，不在此处决定具体商品；不同业务域必须使用对应的版本化属性 Schema。

  4. 映射主题类型
    • brand：围绕一个品牌浏览商品。
    • product：寻找或比较具体商品、品类或领域属性。
    • activity：围绕节日、季节或场景组合商品。
    • 说明：成分、功效、口味、材质、尺寸、规格等都属于领域属性，不新增主题类型，通常路由到 product。
Output

输出 ThemeIntent

输出 theme_type、catalog_domain、attribute_schema_version、entity_type、canonical_entity、shopping_intent、shopping_goal、needs、must_include、must_exclude、search_terms、reason 与 confidence。下一步系统据此验证实体、领域属性、来源和商品覆盖，再决定模板是否放行。

01

品牌主题模板 topic-brand

关键词可唯一解析为品牌实体，且所选站点可售 / 可配送的品牌商品达到模板的 min_products 时使用；页面突出品牌定位、核心系列与品牌商品，隐藏重复的品牌组件。

02

商品导购模板 topic-product-guide

关键词指向具体商品、品类或领域属性，且相关可售商品达到模板的 min_products 时使用；页面以商品发现为主，仅在代表品牌及其商品证据充分时展示品牌组件。

03

场景活动模板 topic-activity

关键词表达节日、季节、使用场景或营销活动，且商品覆盖模板的 required_categories 时使用；页面强化主题叙事与跨品牌选品，品牌组件仍按证据条件展示。

AI 负责理解，规则负责放行

AI 必须输出 theme_type、catalog_domain、attribute_schema_version、entity_type、canonical_entity、shopping_intent、shopping_goal、needs、must_include、must_exclude、search_terms、reason 和 confidence。theme_type 只允许 brand、product、activity；catalog_domain 决定可用的分类与领域属性 Schema。confidence 仅用于解释和决定是否重判，不能代替目录证据，也不能单独决定放行。

AI 判断 语义条件 系统验证条件 通过结果
brand
品牌主题		 关键词主要指向一个品牌，购物意图是了解品牌、系列或品牌商品。 canonical_entity 能精确命中品牌 ID 或已批准别名；该品牌在所选站点存在可售 / 可配送商品，且候选数量达到模板的 min_products。 使用 topic-brand；隐藏 BrandSpotlight，避免与主题 Hero 重复。
product
商品导购		 关键词主要指向商品、品类或领域属性，购物意图是比较、筛选或购买相关商品。 实体能命中所选站点的商品目录、类目、结构化属性或批准的同义词映射；相关商品达到 min_products，且可售 / 可配送状态、站点链接与主图有效。 使用 topic-product-guide；仅在存在证据充分的代表品牌时展示 BrandSpotlight。
activity
场景活动		 关键词主要表达节日、季节、使用场景或营销活动，购物意图是围绕场景完成组合选购。 主题能命中批准的场景词表或活动配置，或能生成可解释的类目查询；候选商品达到 min_products，并覆盖模板要求的 required_categories。 使用 topic-activity；代表品牌能够解释选品时才展示 BrandSpotlight。
uncertain
冲突或不明确		 AI 给出多个主题类型、缺少 canonical_entity、理由与类型不一致，或 confidence 为 low。 系统把未命中字段、冲突证据和候选商品数量返回 AI，仅允许重新判断一次；不把不明确主题默认改成商品导购。 重判通过则继续；仍不通过时输出 route_blocked，并返回可读的 blocked_reason。
route_ready = schema_valid ∧ entity_verified ∧ source_allowed ∧ eligible_product_count ≥ template.min_products ∧ required_categories_covered

品牌主题和商品导购必须验证站点目录实体；场景活动可以没有同名目录实体，但必须能映射到批准的场景规则或活动配置。02 使用 CatalogCoverageProbe 验证候选数量与类目覆盖，只决定模板是否可执行；最终商品池、Product Type 和场景支撑统一由 03 从同一 CatalogSnapshot 冻结。min_products 与 required_categories 由版本化模板配置提供，不由 AI 临时决定。

ThemeIntent 与路由证据

每次匹配必须保存 theme_type、catalog_domain、attribute_schema_version、entity_type、canonical_entity、shopping_intent、shopping_goal、needs、must_include、must_exclude、search_terms、confidence、reason、matched_sources、eligible_product_count、covered_categories、template_id、template_version、module_contracts、brand_module.policy、route_reason、route_status、blocked_reason 与 recheck_count。品牌主题的策略为 hidden；非品牌主题只标记 eligible_with_evidence，最终是否展示由 04 根据商品与品牌证据决定。后续 Review 若要求换模板，系统从模板路由后的选品与组件配置步骤重新运行，而不是在生成后的页面上直接改结构。

04.2 · ShortcutRail module

精选分类 ShortcutRail

它不是品牌全量目录，而是帮助用户快速进入购物意图的一级入口。03 已冻结商品的唯一 Product Type；本阶段只决定展示哪些分类、分类顺序及每类最终使用的代表商品，并创建圆形缩略图任务。

Input ProductTaxonomy

PrimaryPool、每个商品唯一的 Product Type、可售状态、商品图、来源链接与组件容量规则。

Decision 展示与分配

选择 5–8 个可展示分类，确定稳定顺序，并为每类分配 1–2 个最终代表商品。

Asset task 分类缩略图任务

记录代表商品、视觉线索、600×600 WebP 规格与圆形 full-bleed 裁切安全区，不在本阶段生成图片。

Output ShortcutRailPlan

03.1 · Two-layer product pools

自动选品与双层商品池

系统先根据 ThemeIntent 建立精准主题核心池，为商品冻结唯一 Product Type，再用核心商品派生搭配、相似关系与可支撑场景。03 只冻结可复现的选品事实，不决定组件最终 SKU，也不生成文案或图片。

Input

输入

状态为 selection_ready 的 ThemeIntent 与 TemplateRoute、所选 site 对应的同一 CatalogSnapshot、可售 / 可配送状态与模板商品容量要求。

Process

处理

先硬过滤商品并构建精准主题 PrimaryPool，再冻结唯一 Product Type、场景支撑证据和带锚点关系的 RelatedPool；弱相关商品不得补齐核心池。

Output

输出

输出已冻结的 ProductPools、ProductTaxonomy 与 SupportedScenes。SupportedScenes 只记录场景候选、商品锚点与覆盖证据，不包含最终文案、组件槽位或图片。数量不足但仍满足模板最低条件时标记 degraded；无法满足选品硬门时输出 selection_blocked。

01

读取意图与可售全集

读取 ThemeIntent 和所选站点的同一 catalog snapshot，按 site、可售 / 可配送状态、商品身份与来源完整度执行硬过滤。

  • 输入主题实体、购物意图和模板约束
  • 输出可参与评分的 eligible_products
02

构建 PrimaryPool

只保留精准符合主题词和 ThemeIntent 的商品，保存 relevance_score、matched_signals 与 selection_reason。

  • 核心组件只从该池取商品
  • 数量不足时标记 degraded 或 selection_blocked，不由弱相关商品补位
03

归类商品并判断场景支撑

按核心用途、形态和使用阶段为每个 PrimaryPool 商品冻结唯一 Product Type，并根据功能、步骤和商品覆盖输出 SupportedScenes 候选。

  • 保存分类规则、判断依据、场景商品锚点与覆盖证据
  • 覆盖不足的场景降级或删除，不生成最终标题、描述或场景图
04

派生 RelatedPool

以 PrimaryPool 商品为锚点扩展关联商品，并严格区分搭配购买与相似替代两种关系。

  • complementary：补充步骤或完成完整 Routine
  • substitute：同功能、关键属性或品牌替代；价格不参与替代关系判断
05

验证并冻结选品结果

验证池边界、Product Type 唯一性、关系锚点、场景覆盖与商品来源，计算结构哈希后冻结 03 的输出。

  • 输出 ready、degraded 或 selection_blocked，并保存失败原因
  • 组件排序、槽位分配和最终 QA 分别留给 04 与 06
Product Type 随业务域切换

分类数量、名称与领域属性不是全站固定值。Runner 必须根据 catalog_domain 加载版本化 ProductTaxonomy：美妆关注品类、成分与功效；食品关注食品类型、口味、配料、过敏原与饮食标签；家居关注材质、尺寸、空间与安装条件；日用关注功能、规格、包装数量、香型与适用对象。

03.3 · PrimaryPool selection

主商品池的选品逻辑

PrimaryPool 适用于美妆、食品、家居、日用等业务域，只保留同时符合主题语义、购物意图且当前可售的商品。AI 按 catalog_domain 与对应属性 Schema 生成选品条件，商品目录负责验证商品身份、领域属性、库存和素材；数量不足时减少展示，不使用弱相关商品或 RelatedPool 补位。

01

读取主题并解释购物意图

读取上一步已冻结的 ThemeIntent、catalog_domain 与 attribute_schema_version，不重新判断主题类型或模板路由。AI 从目标实体、购买目标、约束条件和使用场景中生成 shopping_goal、target_entity 与 needs，并加载对应业务域的属性 Schema，作为下一步选品条件的依据。

  • 品牌型：browse_brand，限定目标品牌，优先核心系列与代表商品
  • 商品导购型：find_product，限定业务域 Product Type 与结构化领域属性
  • 场景活动型：build_assortment，按已批准的场景角色、必需类目和共享约束形成组合需求；护肤 Routine 只是美妆域的一种场景
  • 示例：ANUA → 品牌商品；无糖抹茶零食 → 口味、糖分与过敏原；小户型厨房收纳 → 尺寸、材质与空间；洗衣日用补给 → 功能、规格与适用对象
02

生成条件并召回候选

系统先使用 GenerationBrief 中已冻结的 site 选择美国站或加拿大站的 CatalogSnapshot；AI 再将购物意图转换为 must_include、must_exclude、主题条件和业务域属性条件，从该快照召回候选商品。

  • 站点边界：site 只允许 us 或 ca，决定目录、链接以及可售 / 可配送范围，由用户选择并由系统执行，不由 AI 推断或参与相关性评分
  • 主题条件：品牌和 Product Type 仅在 ThemeIntent 明确要求时用于筛选
  • 领域条件按 Schema 读取：美妆的成分 / 功效，食品的口味 / 配料 / 过敏原，家居的材质 / 尺寸 / 空间，日用的功能 / 规格 / 香型 / 适用对象
  • 价格及其币种仅作为 CatalogSnapshot 的下游展示与 QA 事实；币种由 site 配置派生，两者都不得进入 PrimaryPool 的筛选、相关性评分、排序或补位逻辑
  • 保存每个候选命中的主题与购物意图信号；AI 只生成非价格检索条件，商品属性必须由目录或允许来源验证
03

验证并过滤商品

移除主题或购物意图不匹配、不可售、证据不足、素材缺失和重复 SKU；销量高不能覆盖任何硬过滤失败项。

  • 验证商品身份、类目、业务域属性、site、可售 / 可配送状态、库存、图片、链接、来源和更新时间
  • 仅保留直接匹配或有明确业务证据的商品
04

排序并冻结 PrimaryPool

先按主题与购物意图匹配排序，再看可售稳定性、组件适配和素材质量，最后用销量与多样性处理同级候选。

  • 保存 catalog_domain、attribute_schema_version、matched_signals、selection_reason、source_refs 与 Product Type
  • 输出 ready、degraded 或 blocked；数量不足时减少展示，不由弱相关商品补位
核心边界

Theme Hero、精选分类、从这里开始、热门精选、品牌组件及探索更多的 All / 分类 Tab 只读取 PrimaryPool。RelatedPool 仅用于搭配购买和相似替代，不能补齐核心池。

05.3 · Image production

三种图片生成模式

图片系统只执行 PagePlan 中已冻结的资产任务，不在生成阶段替换商品或改变组件结构。目标生产模式是“真实商品抠图＋模板背景”，它能兼顾品牌准确性与批量一致性；参考图生成适合快速原型，但必须增加包装文字检查。

Fastest

A · 原商品图裁切

直接使用商品卡主图，统一尺寸和圆形裁切。速度最快、商品最真实，但背景和视觉语言不一致。

Production target

B · 抠图＋模板合成

保留真实包装像素，自动移除背景，再放入版本化的品牌场景模板。适合稳定批量生产。

Current prototype

C · 参考图生成

以商品图作为身份参考，让模型统一背景与构图。视觉自由度高，但可能改写包装细节。

任务：生成 {brand} 的 {category_zh} / {category_en} 分类缩略图。

身份约束：
- 只使用已选择的真实商品参考图：{selected_product_ids}
- 保持商品包装形状、主色、开合方式与品牌识别
- 不新增商品、Logo、标题、价格、折扣、评分或 UI

统一视觉：
- 1:1 正方形，适配圆形 full-bleed 裁切
- 商品位于中心安全区，主体 1–2 个
- 浅色韩系棚拍，柔和自然阴影
- 使用 {category_visual_cue} 表达分类，不遮挡包装

输出：
- 600 × 600 WebP
- 文件名：category-{category_slug}.webp
- 记录 prompt_version、source_images、output_hash

05.1 · Page generation

按组件生成完整英文页面

系统读取状态为 plan_ready 的 PagePlan，按依赖顺序生成英文文案与图片资产，并将组件 Props 确定性装配为 PageGenerationSpec。05 不重新决定组件显隐、顺序或商品分配；每个生成节点独立保存输入、输出和状态。

Input

输入

状态为 plan_ready 的 PagePlan、已冻结商品池、来源证据、英文内容规则与图片资产约束。

Process

处理

按依赖顺序生成英文内容和图片资产，实例化数据契约，再将结构化 Props 确定性装配为桌面与移动端预览。单个生成节点失败时只重试所属节点，并在允许时使用安全回退。

Output

输出

输出 PageGenerationSpec 与 Preview，状态为 generation_ready 或 degraded；必需内容或资产无法生成时输出 generation_blocked。

ThemeHero

主题命题与主张

  • 从 ThemeIntent 与已批准证据生成一句定位、最多两行说明和 2–3 个标签；每项主张都要引用证据。
  • 使用 PagePlan 已分配的 2–3 个主商品生成主视觉，不得在 05 临时替换商品；商品不满足要求时返回 04 重新分配。
  • 根据主图底部颜色选择深色 / 浅色前景；移动端可使用主色渐变遮罩，桌面端保持独立背景结构。

输出ThemeHeroProps + hero-image.webp
阻塞条件unsupported_claim | ambiguous_entity | product_identity_mismatch

一级购物入口

  • 按照“精选分类图片生成与装配”流程生成 category-*.webp，并保存资产 manifest 与节点自检记录。
  • 每个分类链接到“探索更多”的同 ID Tab；不维护第二套筛选体系。

输出ShortcutRailProps + category-*.webp

  • 为每个场景生成能解释任务的英文内容与情境图，商品 ID 和顺序保持 PagePlan 不变。
  • 生成前验证同一场景没有近重复 SKU；若分配不合格则返回 04，不在 05 自动换品。

输入page_plan.start_here + supported_scenes + locale
输出ThemeProductListProps
容量3..5 themes × template-defined product slots

  • 品牌简介只压缩批准资料，代表商品必须属于同一品牌且与当前主题相关。

  • 保留 anchor_product_ids、relation_reason 与 substitute 的未展示状态，不在生成时改写关系。
  • 分页、加载更多和排序使用 PagePlan 与 CatalogSnapshot 数据，不在组件代码中写死总数。

05.2 · English content

按所选站点生成一份英文内容

每次运行只输出所选销售站点的一份英文页面：美国站使用 en-US，加拿大站使用 en-CA。商品事实、实体 ID 和模块结构来自该站点已冻结的数据；AI 只在证据边界内生成对应 locale 的英文文案、标签和可访问性文本。

Stable 实体 ID

SKU、category_id、theme_id、module_id 和资产引用在整条生成链中保持稳定。

Generated 英文文案

标题、说明、标签、alt、ARIA 和链接文案按 site 映射的 en-US 或 en-CA 生成自然英文。

Frozen 商业事实

价格、库存、规格、排序和商品集合必须来自同一 CatalogSnapshot。

Verified 证据引用

内容英文生成规则必须保留验证方式
品牌与系列名称使用官方英文名称，不自行翻译或改写商标。大小写、数字和系列符号品牌术语表匹配
商品名称保留品牌、系列、核心成分、品类和规格，仅规范英文语序。浓度、单位、容量、套装数量字段级 token 对比
营销与场景文案基于证据生成简洁自然的英文表达，不扩写未经证实的功效。证据边界与使用顺序evidence_ref 完整性
评论只显示英文原文评论；无可靠英文评论时隐藏模块。原始文本、作者、评分、商品review_id 回溯
可访问性文本根据真实商品和场景生成英文 alt 与 ARIA label。商品身份和交互目的语义与可访问性检查
输出边界

每次生成只包含一个由 site 确定的 locale：us → en-US，ca → en-CA；不会在同一次运行中混合两个站点。中文仅用于这份流程文档的说明，不进入 PageGenerationSpec、组件 Props 或发布页面。

07 · User review

最终 Review 是唯一人工确认门

系统把完整英文页面、自动 QA 结果、来源证据和本次变更一起提交给用户。用户只做最终确认或提出定向修改，不参与前期模板、选品和组件配置。

Input

输入

状态为 review_ready 的 ReviewPackage：完整预览、QAReport、来源证据、版本差异与不可变 spec_hash。

Process

处理

用户检查内容、选品、组件顺序、图片和响应式表现，只做确认或提出定向修改。修改意见映射回所属阶段，局部重跑后必须重新通过自动 QA。

Output

输出

输出不可变 ReviewDecision，包含 decision_id、spec_hash、decision、reviewer、reviewed_at、feedback_targets 与备注：approved 才进入发布；changes_requested 返回对应节点；rejected 停止本次运行并保留证据。

Preview 完整页面

桌面与移动端真实渲染，包含全部组件、商品、英文内容和图片。

QA 检查报告

展示通过项、自动修复记录、剩余风险和组件级验证证据。

Trace 来源回溯

商品、文案、评论和图片都能回到对应 source_ref 与 observed_at。

Diff 变更范围

标明模板版本、商品集合、组件配置和资产相较上一版本的差异。

01

打开 ReviewPackage

锁定 PageGenerationSpec、QA 报告、预览地址和证据清单。

02

检查完整页面

核对内容、选品、模块顺序、图片、桌面与移动端表现。

03

确认或提出修改

通过则进入发布；修改请求必须指向模板、组件、商品、内容或资产字段。

04

冻结 Review 结果

记录 reviewer、reviewed_at、结论、备注和被批准的 spec_hash。

用户结论系统状态下一步重跑边界
确认approved生成不可变发布包不重跑
需要修改changes_requested返回意见对应的所属阶段并再次自动 QA只重跑受影响节点及其下游
拒绝rejected停止发布并保留证据由新 Brief 重新开始
不在成品上直接改

任何修改都映射回模板、组件配置、商品分配、英文内容或图片资产，再从受影响节点生成并自动 QA；页面预览始终是结构化 Spec 的结果。

08 · Publish

确认后发布，并保留回滚证据

发布只接受已通过自动 QA 且用户确认的 spec_hash。系统冻结页面、内容和资产版本，执行构建与烟雾测试，并把部署结果、来源证据和回滚入口写入发布记录。

Input

输入

状态为 approved 的 ReviewDecision、一致的 spec_hash、内容与资产哈希，以及上一稳定版本。

Process

处理

冻结发布包、编译并部署页面，随后执行公开 URL、关键路由、资源、商品链接和响应式烟雾测试。任一硬门失败即自动回滚上一稳定版本。

Output

输出

输出 ReleaseRecord，包含 release_id、spec_hash、deployment_id、URL、status、deployed_at、smoke_test_report 和 previous_release_id；失败时额外保存 rolled_back 状态、失败原因与回滚目标。

Gate 发布前提

QA 全部通过，user_review = approved，且审核的 spec_hash 未发生变化。

Package 不可变版本

冻结 PageGenerationSpec、site、locale、currency、对应英文内容、商品快照、资产 manifest 和规则版本。

Deploy 发布与检查

构建发布页面，检查状态码、关键路由、组件渲染和桌面 / 移动端访问。

Record 证据与回滚

保存 release_id、URL、commit、部署时间、验证结果和上一稳定版本。

01

冻结发布包

校验已批准的 spec_hash、content_hash 和 asset_manifest_hash 未发生变化，再计算 release_bundle_hash；禁止在发布阶段隐式改写 Spec。

02

编译页面

由已批准 Spec 装配现有组件，生成可部署的英文主题页。

03

部署与烟雾测试

验证公开 URL、首屏、锚点、商品链接、资源加载和响应式布局。

04

记录或回滚

成功则写入发布记录；失败则回滚上一稳定版本并保留失败证据。

发布硬门

没有已批准的 user_review、Review 后 spec_hash 发生变化、关键烟雾测试失败，任一条件成立都禁止发布。回滚不会覆盖失败记录。
