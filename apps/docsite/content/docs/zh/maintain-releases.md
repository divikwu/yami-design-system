适用于上游维护者与发布负责人。输入是一项范围清楚、经过验证的 PR；输出是可追溯的公共版本、更新说明，以及各 Fork 可以执行的同步建议。

## 先区分三件事

| 事项 | 实际改变什么 | 不代表什么 |
| --- | --- | --- |
| 合并上游源码 | 上游分支包含新的公共能力 | 不代表已更新线上 Storybook。 |
| 发布预览或站点 | 指定环境运行某个已确认 commit | 不代表所有 Fork 都已同步。 |
| Fork 吸收更新 | 某个项目合入并验证上游变更 | 不代表其他项目自动兼容。 |

当前组件库以私有 workspace 源码包使用；Changeset 和 Registry 元数据不是已建成的远程 npm 发布与自动升级平台。使用 commit 标识实际代码基线，不仅依赖页面显示的版本号。

## 审核公共改动

1. 确认贡献对应已接受的能力范围，业务内容与无关改动没有混入。
2. 对照实现、Usage、元数据和 Story，检查默认行为、状态与公共导出一致。
3. 检查参数、Token、交互和视觉变化对现有使用方的影响。
4. 检查验证证据、生成文件、无障碍、双语及目标屏幕尺寸。
5. 确认素材可在目标环境使用，预览不包含未授权的业务信息。

负责人要阅读最新 PR 差异和对应 CI 结果，不能只引用上一轮截图或更早 commit 的测试结论。

## 记录版本与兼容性

共享包变化使用仓库现有的 Changesets 工具记录；在仓库根目录执行：

```bash
pnpm changeset
pnpm changeset:status
```

前者交互式创建变更记录，后者查看待处理的变更状态。选择实际受影响的包，并与维护者确认变更级别；它们不会自动完成站点部署。

现有配置关闭自动 Changelog 和自动提交，并忽略 Canvas、Storybook 两个应用包。因此应用发布情况和完整迁移说明仍需由负责人记录，不应假设工具会替团队完成。

至少说明：

- 修复了什么或新增了什么，涉及哪些组件与调用方。
- 现有参数与默认值是否保持，是否需要修改业务页面。
- 视觉、交互或数据形状是否变化，即使类型仍能通过也要说明。
- 推荐的上游 commit、迁移步骤、已知限制与回退基线。

若修改存在破坏性影响，先给出迁移方案和验证范围再合并；Alpha 阶段也不应以“尚未稳定”为由省略说明。

## 验证与合并

在最终变更上运行 `pnpm validate`，并根据范围完成 Storybook 浏览器测试、构建、文档索引与相关视觉或端到端检查。项目 CI 的必需检查也必须通过。

自动检查不代替实际预览。使用固定数据核对关键场景，保存测试的语言、主题、屏幕尺寸和结果，避免把未覆盖状态写成通过。

由具备权限的维护者在评审完成、差异确认且合并获授权后执行合并，记录最终上游 commit。不要让 AI 因为“检查全绿”自行扩展为合并或发布。

## 单独安排部署

现有策略要求 Preview 与 Production 部署手动执行并获得单独授权，Git 推送或合并不会自动更新站点。

发布前确认目标项目、环境、源 commit、负责人、访问范围、资产使用权限和回退版本。部署后打开真实页面验证渲染与关键交互，记录 URL 及实际运行版本。

本指南采用私密协作模式，但代码仓库私密不等于已部署站点私密。现有部署策略与目标访问范围不一致时，先由负责人调整访问方案，不将保密内容发布到公开预览。

## 通知 Fork 同步

用下面的信息发布团队更新通知；同步时机由各项目负责人结合当前任务决定。

```text
上游更新：[范围及解决的问题]
推荐基线：[commit]
受影响组件：[列表]
兼容性：[无需改调用 / 需要迁移，附步骤]
验证入口：[允许访问的预览与固定数据说明]
项目需检查：[关键页面与交互]
已知限制：[说明]
负责人及反馈位置：[填写]
回退基线：[此前已验证 commit]
```

每个 Fork 完成更新后仍需检查自己的页面。共同维护上游版本不意味着由上游负责人替所有项目发布。

## 出现问题时回退

先停止受影响版本的进一步推广，记录问题范围和当前部署，不覆盖其他人的工作。

源码问题由维护者通过受评审的修复或回退 PR 处理；已经部署的站点需要另行授权恢复此前验证过的版本。Fork 保留自己的已验证基线，并在恢复后重新检查页面。

不要用强制同步或重写共享历史作为默认回退方式。记录恢复到哪个 commit、哪个环境、验证结果和后续修复负责人。

## 常见问题

**CI 通过是否等于上线？** 不是。还需要评审与合并决定；部署是另一项单独授权的操作。

**有 Changeset 是否已经发布 npm 包？** 不是。当前是 workspace 源码协作，不能据此承诺可远程安装或自动升级。

**只改文档也要部署吗？** 本地文件、GitHub 源码与托管站点是不同状态。需要让站点展示新内容时，仍须按发布流程处理。
