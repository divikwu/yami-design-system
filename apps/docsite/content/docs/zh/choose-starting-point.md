适合已经明确页面目标、准备交给 AI 实现的任务。本页先判断是否有页面参考，再提供对应提示词，并帮助确定结构、内容归属、复用范围与验收要求。

## 先判断参考情况

| 现有输入 | 页面起点 |
| --- | --- |
| 有接近的 YAMI Page Story | 复用页面结构、类型和公开组件，在任务自己的 Story 与 fixture 中替换内容 |
| 只有组件参考 | 先根据用户任务列出页面模块，再用已有组件完成最小页面组合 |
| 有设计稿、截图或网页 | 把参考拆成结构、内容、组件、响应式和交互，不把视觉相似当作完整需求 |
| 没有页面或组件参考 | 从用户任务和内容层级出发，搜索 YAMI Pages 与 Components 后再提出新结构 |

无论有没有参考，都要先写清用户要完成什么。参考决定从哪里开始，不替代真实内容、交互和验收标准。

## 复制页面提示词

### 有页面参考

```text
请在当前 YAMI 项目中创建一个独立页面版本。

页面目标：<需要完成什么任务>
目标用户：<最终使用页面的人>
页面参考：<Page Story、设计稿、截图或已获准使用的网页>
内容与素材：<中英文文案、商品、图片、数据及来源>
需要保留：<参考中的结构、组件或交互>
需要修改：<本次页面的具体变化>
必须实现的交互：<按钮、链接、筛选、弹层或提交结果>
验收标准：<需要确认的语言、主题、屏幕尺寸、状态和交互>
可选补充：<素材权限、数据版本及不在本次范围的内容；没有则写“待确认”>

- 先检查最接近的页面和组件，说明哪些可以直接复用、哪些需要页面实现、哪些需要新能力，再开始创建。
- 只处理本次需求，不覆盖默认示例，不修改无关文件。
- 使用外部参考时，只使用已获准的结构、内容和素材。
- 完成后在 Storybook 中验证真实页面和主要交互。
- 告诉我：参考使用方式、修改文件、Story 地址、验证结果和未解决项。
- 不要提交、推送或发布。
```

### 没有页面参考

```text
请在当前 YAMI 项目中创建一个页面。

页面目标：<需要完成什么任务>
目标用户：<最终使用页面的人>
内容与素材：<中英文文案、商品、图片、数据及来源>
必须实现的交互：<按钮、链接、筛选、弹层或提交结果>
验收标准：<需要确认的语言、主题、屏幕尺寸、状态和交互>
可选补充：<素材权限、数据版本及不在本次范围的内容；没有则写“待确认”>

- 先搜索现有页面和组件，列出最接近的起点；有合适结构就复用，没有时再提出最小的新页面结构。
- 只处理本次需求，不修改无关文件，不编造价格、库存、功效或未提供的业务规则。
- 完成后在 Storybook 中验证真实内容、响应式和主要交互。
- 告诉我：选用的页面结构、组件清单、修改文件、Story 地址、验证结果和待确认项。
- 不要提交、推送或发布。
```

## 找最接近的页面

| 任务 | 参考入口 | 重点观察 |
| --- | --- | --- |
| 电商首页和内容发现 | [Ecommerce Home](https://yami-design-system-storybook.vercel.app/?path=/story/yami-pages-ecommerce-home--pc) | 商品模块、导航和内容顺序 |
| 搜索与筛选 | [Search Results](https://yami-design-system-storybook.vercel.app/?path=/story/yami-pages-search-results--results) | 筛选、空结果和结果列表 |
| 商品详情 | [Product Detail](https://yami-design-system-storybook.vercel.app/?path=/story/yami-pages-product-detail-beauty--pdp) | 商品信息、规格和详情交互 |
| 品牌活动与内容专题 | [Topic Landing Page](https://yami-design-system-storybook.vercel.app/?path=/story/yami-pages-topic-landing-page-brand--pc) | 主视觉、分类和商品集合 |

这些是维护中的页面组合，不是可以直接发布的业务项目。图片、链接、价格和交互反馈需要按任务核对。线上 Storybook 与本地版本也可能不同，制作前记录采用的代码基线。

## 判断改动层级

| 需求变化 | 优先做法 | 避免 |
| --- | --- | --- |
| 只改商品、图片、文案 | 新建任务数据或 Story，复用原页面 | 覆盖默认 fixture，让其他示例也变化 |
| 调整模块顺序、增减模块 | 在独立页面组合中使用公开组件 | 把整页实现复制成多个长期分叉 |
| 现有组件少一个通用状态 | 先反馈缺口，确认是否增加变体 | 为单个活动修改所有页面的默认样式 |
| 用户目标和信息结构完全不同 | 定义新页面任务，复用可用模块 | 强行塞进不合适的页面类型 |

fixture 是保存示例内容的数据文件，Story 是运行某个组合的展示入口。使用公开组件，并不代表要把整个参考页面的源码复制一份。

## 明确内容归属

页面的商品、业务链接、文案与状态由自己的项目负责。公共组件负责约定的交互、样式、主题和可访问性。

例如，页面可以向 ProductCard 传入商品信息和点击处理；不能为了某次活动复制一套 ProductCard，或直接改公共 Token 改变其他页面。

团队协作中，先把项目内容留在自己的 Fork。一个能力在多个任务中都能复用、并补齐用法与验证后，再按[分享组件与页面](/zh/docs/contribute-upstream)提出独立 PR。

## 继续调整页面

已有页面需要修改时，继续使用下面的提示词：

```text
请继续调整当前页面。

需要修改：<具体内容、布局或交互>
必须保留：<不应变化的结构、内容和行为>
验收标准：<需要重新检查的语言、主题、屏幕尺寸、状态和交互>

- 先确认修改范围，只处理本次内容，不修改无关文件。
- 完成后在 Storybook 中重新验证，并告诉我修改文件、Story 地址、验证结果和未解决项。
- 不要提交、推送或发布。
```

## 检查起点是否合适

打开参考示例，在目标屏幕上走一遍主要路径。能否用现有结构表达需求？需要变化的是数据、组合还是组件本身？是否有某个关键交互根本不存在？

拿不准时，先让 AI 列出“可以直接复用 / 需要页面实现 / 需要维护者确认”三类，再决定下一步。不要以生成更多文件替代这个判断。

## 检查页面结果

确认 AI 最终报告：

1. 检查过哪些 Pages、Components、Story 和规范。
2. 为什么选择复用现有页面、重新组合或建立新页面结构。
3. 修改了哪些 Story、fixture、素材和实现文件，是否影响公共组件。
4. Storybook 中实际打开了哪个页面 Story。
5. 实际检查过哪些语言、主题、尺寸、状态和主要交互。
6. 哪些命令通过、哪些未运行或失败，以及仍需确认的内容。
