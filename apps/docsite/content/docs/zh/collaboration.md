团队采用的协作方案是：私密上游维护公共组件，获得授权的成员在自己的 Fork 中制作页面；验证稳定的公共能力通过小范围 PR 回到上游，其他成员再主动同步。

这是一套需要团队执行的工作方式，不是已经配置完成的自动协作平台。本文不会改变仓库权限，也不会自动创建 Fork、共享预览或部署页面。

## 开始前

请先让项目负责人确认三个条件：

- 上游仓库、组织策略和成员权限已满足私密 Fork 的要求。
- 你知道谁负责业务需求、页面制作、评审和发布；同一人可以兼任。
- 团队已说明允许使用哪些数据和素材，以及预览可向谁开放。

权限尚未准备好时，先阅读示例或整理需求，不要把内部内容上传到未经确认的仓库。

## 理解三个位置

| 位置 | 放什么 | 不做什么 |
| --- | --- | --- |
| 上游主项目 | 稳定规范、公共组件、通用页面模式及其验证 | 不收录每个活动的完整业务工作 |
| 你的 Fork | 独立制作所需的代码、任务分支和评审记录 | 不把自己的整个仓库合并回上游 |
| 任务分支 | 某个页面或一次明确调整 | 不直接在同步用的 main 上制作 |

Fork 的 `main` 保持干净，用来接收上游的已确认更新。页面内容和业务调整保留在任务分支。

任务分支记录一个工作方向；提交记录可恢复的检查点；预览链接用于查看某个已标明版本的结果。三者不能相互代替。

## 分清各自职责

| 角色 | 需要给出的信息或决定 |
| --- | --- |
| 需求负责人 | 用户任务、内容来源、业务限制和验收目标 |
| 页面制作者 | 页面实现、改动范围、固定版本和可运行结果 |
| 评审者 | 可复现的问题、修改优先级以及是否通过 |
| 核心库维护者 | 复用边界、公共贡献 Review 和上游版本维护 |
| 发布负责人 | 目标环境、访问权限、发布批准及上线后检查 |

不熟悉 Git 的同事可以让 Codex 或工程协作者执行操作，但不能省略范围确认。AI 负责执行和提供证据，人负责业务、权限与发布决定。

## 跟随一次协作

1. 在自己的授权 Fork 中，从已确认的上游基线开始一个任务。
2. 给 AI 提供参考页面、需求和可使用的素材，限定本次修改范围。
3. 保存阶段结果，按[统一检查清单](/zh/docs/review-checklist)完成自检。
4. 提供有访问权限、固定代码与数据版本的预览，请同事评审。
5. 页面业务成果在自己的项目中交付；公共组件缺口单独交给维护者判断。
6. 有通用价值的改动拆成聚焦 PR，不携带活动文案、私密数据或无关业务代码。
7. 上游接受并验证后，其他成员按自己的任务节奏同步、检查并更新预览。

可把这段约定交给 AI：

```text
我在团队授权的 Fork 中制作一个页面。
请先确认当前目录、分支、未提交改动和上游来源。
不要直接修改同步用的 main；本次只处理已确认的任务。
发现公共组件缺口时先说明，不擅自扩大修改范围。
提交、推送、贡献 PR 和部署分别等待明确授权。
```

## 你应该看到什么

每个任务都有负责人、独立工作位置、可恢复的版本和评审入口。别人开始新任务时，不需要等待你结束编辑同一个文件夹。

公共改进可以逐步回馈，但不会自动改变所有 Fork。上游合并也不会自动更新每个人正在看的预览或生产页面。

当前包以 workspace 源码方式消费；不要把本流程理解成已完成独立包安装、自动升级或任务看板。未来若采用版本化分发，应另补安装与升级指南。

## 遇到问题时

- **不知道该改页面还是组件**：先记录缺口，读[组件缺口反馈](/zh/docs/component-gaps)。
- **两个人准备改同一能力**：先确定一位实现负责人，另一人做评审或独立任务。
- **同事看不到结果**：检查预览权限，不要通过公开内部仓库来解决。
- **不确定能否回馈上游**：先给维护者看最小差异，不提交整条业务分支。
