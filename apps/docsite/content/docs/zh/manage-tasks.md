一个任务对应一个明确的页面目标，而不是“把项目整体优化一下”。你应该能说明这次改什么、保留什么，以及完成后请谁看。

任务分支与独立工作目录帮助隔离改动；它们不是自动的任务管理系统。请把下面的任务记录放在团队约定的位置。

## 开始前

- 已完成[创建自己的 Fork](/zh/docs/fork-project)和[准备环境](/zh/docs/prepare-environment)。
- 已找到[最接近的页面示例](/zh/docs/choose-starting-point)。
- 已确认需求负责人、素材来源和本次允许修改的范围。
- 知道自己的项目目录，没有与另一位同事共用正在编辑的工作副本。

同一台电脑也可能同时有多个任务。若要并行制作，让协作者准备独立工作副本或 worktree，并分配不冲突的服务端口。

## 建立任务记录

先填写一份简短记录，再让 AI 开始：

```text
任务名称：
负责人 / 评审者：
用户要完成的事情：
参考页面或 Story：
本次要改 / 必须保留：
允许修改的目录或文件：
内容、图片和商品来源：
目标语言、主题、屏幕：
工作目录 / Fork / 任务分支：
上游基线 SHA / 当前检查点 SHA：
当前状态 / 下一步：
```

SHA 是某次 Git 提交的唯一标识，用来说明“这一版代码是哪一版”。它不证明浏览器内尚未导出的草稿已保存，也不代表通过评审。

## 开始独立制作

1. 让协作者先确认当前目录、分支、远程来源和未提交改动。
2. 若是全新业务任务，从已同步、干净的 Fork `main` 建立任务分支，例如 `codex/project-summer`。
3. 若是在已有页面上继续修改，从那个页面的已确认任务版本继续，不盲目从 main 重做。
4. 并行任务使用独立目录；记录各自端口，避免启动到另一个任务的页面。
5. 请 AI 先说明计划修改哪些文件，经确认后执行，再打开实际结果检查。

不要直接在用于同步上游的 `main` 上制作页面。发现目录中有其他人的改动时，先确认归属，不替对方提交或删除。

## 保存可恢复的检查点

第一版能运行、准备邀请评审或需要交接时，都适合保存检查点。请明确告诉协作者是否授权创建 Git 提交或推送到自己的 Fork。

```text
请先整理本任务的改动文件和验证结果，说明哪些内容仍未保存。
如包含 Canvas 浏览器草稿，请先导出并确认保存位置。
我确认范围后，再只提交本任务相关文件；不要整仓暂存。
未经另行授权，不推送、不合并、不部署。
完成后给我检查点 SHA、未提交内容和下次继续的方法。
```

浏览器里的 Canvas 草稿属于本地存储。切换浏览器、电脑或 Fork 不会自动带走它；需要按项目方式导出并纳入可交接文件。

提交前检查图片、导出文件和配置中是否含未授权内容。凭证、个人数据和临时调试材料不应随检查点提交。

## 继续或交接任务

继续时提供任务记录和最近检查点，让 AI 先检查现状再修改。不要只说“接着上次做”，也不要假定所有草稿都在 Git 中。

交给另一位同事时，提供 Fork、分支、SHA、所需内容文件、启动入口和未解决问题。对方在自己的授权工作位置重现，不接管你的活动目录。

此时预期能回答三件事：结果在哪里、哪一版可评审、还有什么没完成。换人之后也能继续，而不是依赖原作者的聊天记忆。

## 遇到问题时

- **打开的不是本任务页面**：核对地址、端口和监听服务所属目录，不终止其他任务的服务。
- **AI 改了范围外文件**：暂停，查看具体差异；只处理本次造成的改动，不整仓回退。
- **分支切换受阻**：保留未提交内容，让协作者说明安全保存方案；不要强制切换。
- **有多个同名版本**：用 SHA 和具体预览入口辨认，避免仅按“最新版”交流。
