## 准备好这些信息

- **自己的 GitHub 仓库：** 完成[快速开始](/zh/docs/fork-project)后得到的 Fork 地址。
- **Vercel 账号或团队：** 用来存放这次部署；已有项目时提供项目名称或链接。
- **要分享的内容：** 本地项目位置，以及具体页面或 Story 名称。
- **访问对象：** 仅团队成员，还是允许公开访问。

你负责登录并完成账号授权，AI 帮你处理项目配置和构建。无需把密码或令牌粘贴进提示词。`localhost` 是本机地址，部署完成后才会得到团队成员可访问的网址。

## 首次部署

让 AI 带你完成这四步：

1. 在 Vercel 中创建或选择你自己的项目，连接指定 GitHub Fork。
2. 确认部署 Storybook。当前仓库的应用目录是 `apps/storybook`；AI 应核对构建命令、输出目录和共享组件依赖，避免部署成 Canvas 或文档站。
3. 确认发布内容、部署分支和访问范围，启动构建。首次导入可能生成该项目的正式部署（Production），AI 需要说明它会更新哪个网址。
4. 等待部署就绪，打开具体 Story 检查显示、图片和主要操作，再返回分享链接。

替换下面的信息后，发送给 Codex 或 Kiro：

```text
请把我的 YAMI Storybook 部署到 Vercel，并接入 GitHub 自动部署。
本地项目：<项目目录>
GitHub 仓库：<自己的 Fork 地址>
Vercel：<已有项目链接，或新项目所属的账号 / 团队>
分享页面：<Story 名称或本地页面链接>
访问对象：<仅团队成员 / 允许公开访问>

- 检查已有连接，按 apps/storybook 配置构建，只处理本任务内容，保留其他改动。
- 准备好后说明发布内容、目标和访问范围，以及是否为正式部署；经我确认后再提交、推送和部署。
- 需要登录或授权时告诉我具体操作；无法满足访问范围时先说明，不擅自公开。
- 部署完成后打开页面检查显示和主要操作，返回项目链接、页面链接和检查结果。
```

你自己的 Fork 需要单独连接 Vercel；上游的部署配置不会替你创建托管项目。仓库为私密，也不代表部署后的网站自动私密。访问范围应以实际 [Vercel 部署保护](https://vercel.com/docs/deployment-protection)设置为准。

## 修改后自动更新

Git 自动部署接好后，让 AI 将修改推送到指定任务分支，Vercel 会按项目配置生成新的 Preview（预览）。生产分支的更新会触发 Production（正式部署），因此日常评审使用非生产任务分支。规则见 [Vercel Git 部署说明](https://vercel.com/docs/git)。

```text
请更新这个 Vercel 项目的页面预览。
本地项目：<项目目录>
Vercel 项目：<项目链接>
本次修改及页面：<修改要求和 Story 名称或链接>

- 完成修改和本地检查，保留已确认的内容及其他任务的改动。
- 核对连接的仓库，查找或创建非生产任务分支；检查通过后，授权你只推送本次改动，触发预览部署。
- 不更新正式网站。
- 部署完成后打开页面，检查内容和主要操作。
- 返回本次部署的页面链接、对应版本、变化和未解决问题。
```

同一分支的预览链接会随部署更新；需要团队成员确认某个固定版本时，分享那一次部署的链接，并附上具体 Story 入口。

## 发布正式版本

评审通过后，使用下面的提示词更新正式网址。让 AI 先核对项目的生产分支，不要默认把 Fork 中用于同步上游的 `main` 当作业务发布目标。这段提示词授权发布到填写的目标：

```text
请把评审通过的版本发布到正式网站。
已通过的版本或评审记录：<链接或位置>
目标项目和正式地址：<明确填写>
发布范围：<具体页面或改动>

- 核对版本、生产分支和部署配置，只处理本次发布内容，保留其他任务的改动。
- 检查通过后，按仓库流程提交、推送并合入目标生产分支，触发自动部署；目标不明、检查失败或冲突影响不清楚时先报告。
- 部署完成后核对线上版本，打开正式页面检查主要操作。
- 返回正式地址、发布版本、检查结果和未解决问题。
```

如果正式部署失败，让 AI 保留错误信息和上一版可用地址，说明恢复方案，再按负责人授权处理。不要把数据快照自动换成实时接口，也不要顺便发布其他任务。

## 交给团队成员继续

任务还没完成，也可以先把当前进度交给团队成员。让 AI 将本任务的代码、素材和交接说明提交到一个独立的交接分支，并推送到指定 GitHub 仓库。团队成员拿到仓库、分支和版本链接后，让自己的 AI 拉取这一版继续制作，无需等到评审通过。

**交出当前进度：**

```text
请把这个未完成任务推送到 GitHub，供团队成员接手。
本地项目：<项目目录>
目标 GitHub 仓库：<仓库地址>
任务目标：<最终需要完成什么>
剩余要求：<还需完成什么>

- 只整理本任务的代码和必要素材，保留其他工作；写好交接说明，包含进度、未完成事项、启动方法和页面入口。
- 如实记录检查结果和已知问题，标明这是未完成版本。
- 创建独立的非生产交接分支，提交并推送代码、素材和说明。
- 不合入 main 或更新正式网站。
- 若触发预览，如实报告状态，不以预览成功作为交接前提。
- 确认 GitHub 已包含这次提交，返回交接分支、提交版本和交接说明链接。
```

只有本地提交，团队成员还无法从 GitHub 取得文件；需要确认推送已完成，并确保接收人有仓库读取权限。把 AI 返回的链接发给团队成员，再由团队成员使用下面的提示词。

**接手并继续制作：**

```text
请接手这个未完成任务，并继续制作。
交接版本：<GitHub 提交版本链接>
交接说明：<文件路径或链接>
本次要求：<继续完成什么>

- 在独立目录中获取并核对指定版本，阅读交接说明，保留本地已有工作。
- 创建接续分支，安装依赖并启动页面；无法运行时先报告并处理阻塞。
- 按要求继续修改，保留已确认的内容，检查结果并更新交接说明。
- 返回修改内容、页面入口和检查结果；需要再次交接时再按指定目标推送。
```

## 检查部署与交付结果

- **部署或发布：** AI 已确认部署成功，打开具体 Story 检查内容，并核对接收人能按约定方式访问。
- **交接未完成任务：** 指定 GitHub 分支已包含交接版本，团队成员能拉取同一份代码，并了解已完成内容、未完成事项和当前运行状态。

把链接和希望对方确认的问题一起发给团队成员即可。若构建失败，让 AI 查看部署日志；若链接打不开，检查访问权限；若出现旧内容，核对部署版本和 Story 入口。
