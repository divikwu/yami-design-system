页面交付是把可复现成果和未完成事项交给下一位负责人；发布则是把指定版本部署到经过批准的环境。交付完成不一定需要马上上线。

业务页面成果留在自己的项目中。公共能力另走[选择性贡献上游](/zh/docs/contribute-upstream)，不要把整个业务分支合入核心库。

## 开始前

- 已按[统一检查清单](/zh/docs/review-checklist)完成约定自检。
- 已有[评审记录](/zh/docs/review-preview)，注明批准者、代码 SHA 和数据版本。
- 已列出已知问题、延期项和本次不包含的功能。
- 已确认接收人；需要部署时，还须确认发布负责人和目标环境。

没有部署权限或环境时，可以先完成代码与素材交接。不要把等待发布描述成页面还没有保存，也不要把交接完成描述成已经上线。

## 先说明当前状态

| 状态 | 可以怎样报告 | 尚不能证明什么 |
| --- | --- | --- |
| 本地已保存 | 文件和必要草稿已保存，给出位置 | 别人已经能打开 |
| 已提交到自己的 Fork | 指定分支和 SHA 已可供授权同事获取 | 页面已经部署 |
| 评审通过 | 指定版本已由指定人员确认 | 后续版本也自动通过 |
| 代码已合并 | PR 和目标分支已确认 | 线上环境已更新 |
| 已部署并抽查 | 指定环境展示指定版本，已验证关键路径 | 所有场景都已验证 |

Fork 的 main 用于同步上游，不是默认的业务发布分支。业务 PR 如有需要，应使用团队约定的业务集成分支；交付记录也可以直接指向已确认的任务 SHA。

## 准备交付包

把必要信息集中到同一条交付记录：

```text
任务名称 / 交付人 / 接收人：
用户任务与本次范围：
Fork / 任务分支 / 代码 SHA：
页面或 Story 入口 / 启动方法：
Snapshot、Scenario 或静态内容文件：
必要的导出文件和素材位置：
目标语言 / 主题 / 屏幕：
评审结论 / 批准者 / 记录链接：
执行过的检查及结果 / 未验证范围：
已知问题 / 后续负责人：
当前状态：仅交付 / 等待部署批准 / 已部署并抽查
```

让接收人在自己的授权环境中确认能取得必要文件并打开结果。截图用于理解页面，不替代代码、数据和操作说明。

如果需要提交或推送，由协作者先检查工作区与具体差异，再根据你的明确授权只处理本任务文件。不要整仓暂存，也不要为交付清理别人的改动。

## 单独确认发布

只有明确需要上线时，才进入下面的流程：

1. 指定目标：哪个项目、哪个环境、哪个域名，以及允许访问的人。
2. 确认发布 SHA 与评审版本一致；若发生变化，补充受影响部分的验证。
3. 确认数据模式、素材许可和访问控制；不把 Snapshot 静默换成 Live。
4. 请负责人核对相关 CI 与检查结果，并明确批准本次部署。
5. 由有权限的人执行已配置的部署流程，记录部署标识与来源 SHA。
6. 从目标地址打开实际页面，复查关键路径、资源、语言和主题。
7. 记录结果；若失败，按事先确认的恢复方案处理，不擅自强推或删除历史。

首次部署前，还需要负责人配置并批准宿主、访问控制和恢复方式。本教程不假定每个 Fork 自动拥有预览或生产环境。

仓库现有部署配置关闭自动 Git 部署；推送或合并不等于上线。团队新增环境也应先确认它的实际行为，不能按别的项目的经验判断。

## 你应该看到什么

只交付时，接收人能重现指定版本，并知道剩余问题归谁处理。完成部署时，目标环境、代码 SHA、抽查结论和发布时间都有记录。

如果只是构建成功或收到了 HTTP 200，应报告到这一层，不宣称已证明完整体验。统一检查标准仍以[页面检查清单](/zh/docs/review-checklist)为准。

交付后保留评审和版本记录。上游后续更新需要重新同步与验证，不会自动让已经交付的页面获得新能力。

## 遇到问题时

- **没有发布账号或项目**：请负责人安排环境；保持“交付完成，发布未执行”的准确状态。
- **链接打开的是旧版**：核对部署来源 SHA 和环境地址，不反复提交无关改动触发刷新。
- **代码可访问，页面不可访问**：分别检查仓库授权与预览访问控制。
- **上线后发现问题**：记录影响范围，联系发布负责人；使用批准的恢复方案，不临时覆盖共享历史。

## 下一步

结束本任务并记录后续负责人。准备接收公共更新时阅读[同步上游与处理冲突](/zh/docs/sync-upstream)；核心库维护者另读[维护上游版本](/zh/docs/maintain-releases)。
