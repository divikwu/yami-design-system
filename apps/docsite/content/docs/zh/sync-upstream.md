上游增加组件、发布页面示例或修复问题后，你可以让 AI 把更新带入自己的项目。正在评审或即将发布的页面不必立即升级，先保留已经确认的版本。

## 什么时候需要更新

- 开始新任务前，希望使用团队已确认的组件和页面示例。
- 维护者通知某个修复与你的页面有关。
- 现有任务确实需要上游新增的能力。

不需要为了让 Fork 显示“最新”而打断正在进行的评审。没有具体更新需求时，继续当前任务即可。

## 拉取上游最新版本

用于把共享仓库的最新内容更新到本地项目。上游是团队维护的共享仓库，不是你自己的 Fork；仓库和分支已配置时，让 AI 自动查明即可。

```text
请把上游最新版本更新到我的本地 YAMI 项目。
本地项目：<项目目录>
上游仓库：<GitHub 地址；已配置则自动查明>

- 核对上游仓库和更新分支，未指定分支时使用上游默认分支；无法确定时先问我。
- 获取该分支最新提交，保留本地已有改动，在独立分支中合入更新，不强制覆盖自己的内容。
- 完成相关检查并打开页面；需要改变已确认效果的冲突，先说明差异再让我决定。
- 返回接收的上游版本、更新内容和检查结果，说明原任务是否已更新。
- 本次不推送或发布。
```

已复制或定制的页面需要由 AI 检查是否需要适配。代码更新不会自动更新 GitHub 上的 Fork 或已部署网站，验证后再按下方流程采用。

## 检查本地与 GitHub 是否一致

用于确认本地是否漏了远程更新、是否有尚未推送的提交，或是否有尚未保存为版本的文件改动。比较自己的远程进度时填自己的 Fork；比较上游时填共享仓库。

```text
请检查本地项目与 GitHub 上的版本是否一致。
本地项目：<项目目录>
对比目标：<GitHub 仓库和分支；已配置跟踪关系则自动查明>

- 先核对比较的仓库、本地分支和远程分支，获取最新远程记录；目标不明确时先问我。
- 比较两边的提交和文件内容，检查本地未提交改动及未跟踪文件，不把被忽略的依赖或构建产物算作源码差异。
- 用简单语言说明：是否一致、本地领先或落后哪些内容、是否双方都有改动，以及建议下一步做什么。
- 只检查和报告，不修改工作文件，不提交、合并、推送或发布。
```

即使提交版本相同，本地也可能还有未提交的修改；AI 应分别说明“提交是否一致”和“文件内容是否一致”。无法读取远程最新记录时，应报告未完成核对，不能把缓存记录当作最新结果。

## 冲突时你需要决定什么

“冲突”表示同一部分有两种改法。你不需要直接编辑冲突代码，让 AI 先用页面效果解释差异。

| 冲突内容 | 谁确认 | 请 AI 提供什么 |
| --- | --- | --- |
| 文案、图片、模块顺序 | 需求负责人或制作者 | 更新前后会怎样显示 |
| 已确认的视觉或交互 | 制作者和评审者 | 受影响的位置、方案与预览 |
| 共享组件或页面的规则与接口 | 对应维护者 | 双方目的、影响范围和可兼容方案 |

意图清楚的技术合并由 AI 处理；需要改变已确认体验或存在多种业务选择时，再由你决定。无法判断时保留原版本，暂不接收这次更新。

## 验证后回到原任务

1. AI 打开更新后的页面，使用原内容、语言、主题和屏幕尺寸检查。
2. 你确认页面效果，决定是否采用这一版。
3. 确认采用后，AI 将验证结果合入原任务分支，并记录更新前后版本。
4. 需要团队成员复查时，按已有授权推送任务分支，等待新的预览完成。
5. AI 核对预览版本，更新任务记录，再请评审者检查受影响部分。

如果还有其他人更新原任务，AI 应先检查新差异再合入。普通页面使用同一份示例数据即可；动态数据页面继续使用约定的快照。具体标准见[检查页面](/zh/docs/review-checklist)。

## 怎么判断完成

你要用的公共改进已进入指定任务，原有业务内容仍在，页面能完成原来的操作。AI 已记录版本和验证结果，并说明共享预览是否更新。

只更新了 Fork 的基线、还没更新任务时，应明确报告到这一步；代码更新也不代表正式网站已经变化。

## 常见问题与下一步

更新后页面没有变化，让 AI 核对任务分支和部署版本；检查失败时先保留结果，确认是公共改动还是本地适配问题，不跳过检查直接发布。

需要继续评审，进入[部署与交付](/zh/docs/deliver-publish)。发现其他人也需要的修复，按[分享组件与页面](/zh/docs/contribute-upstream)处理。
