这是页面自查、同事评审和交付共用的验收清单。每次只在同一份任务记录中更新结果，不另外维护三套相似的检查表。AI 可以协助检查，页面目标与发布结论仍由负责人确认。

## 固定这次检查的版本

检查前记录任务、分支、提交或未提交改动说明、Story 或页面地址，以及数据来源。正式评审优先固定 Snapshot；本地 fixture 练习则记录文件路径与 Git 提交。只有分支名，没有具体版本，不能保证下次看到同一结果。

区分三种数据：Scenario 用于稳定复现特定状态，Snapshot 用于固定一次真实数据样本，Live 用于观察当前数据变化。不要把实时价格与固定样例混在同一次前后对比里。

## 使用统一验收清单

在任务记录中逐项填写“通过 / 待修复 / 不适用”，附截图、复现步骤或测试输出。“不适用”必须说明理由；没有检查不能记为通过。

| 检查项 | 通过标准 |
| --- | --- |
| 需求与范围 | 页面完成约定任务；没有偷偷改动公共组件、默认示例或无关页面 |
| 文案与商品 | 标题、说明、商品数量与排序符合需求；没有编造价格、优惠、评价或库存 |
| 图片与链接 | 图片完整加载、裁切合理、替代文本准确；链接目的地可解释，没有把演示动作当成真实购买 |
| 公共能力 | 使用已有页面和公共组件；颜色、排版、间距等消费真实语义 Token |
| 中文与英文 | 两种语言的信息完整且对应；英文长文案不截断关键内容；可访问名称也已本地化 |
| 浅色与深色 | 文字、表面、边框、焦点与禁用态可读；图片没有不合适的底色或透明区域 |
| 窄屏与宽屏 | 至少检查 360、375、402、768、1024、1440px；受影响的超宽布局加查 1920px；没有页面级横向溢出或控件遮挡 |
| 交互与状态 | 所有改动过的按钮、标签页、筛选、排序、弹层和返回路径有明确结果；刷新后状态符合约定 |
| 键盘与无障碍 | Tab 顺序可理解、焦点可见；按组件契约检查 Enter、Space、方向键、Escape；弹层关闭后焦点恢复，没有键盘陷阱 |
| 加载、空态与错误 | 对适用的数据区域检查加载、空列表、长内容、图片缺失和请求失败；未接入网络的静态练习注明网络错误不适用 |
| 动效与浏览器错误 | 减少动态效果设置可用；没有阻碍操作的动效、控制台错误或失败的必要资源请求 |
| 证据与范围 | 记录实际检查的语言、主题、尺寸、数据与命令；未覆盖项和遗留问题明确可见 |

视口清单是验证样本，不是要求为每个宽度新建 CSS 断点。组合检查应覆盖每项改动的风险；不能只看默认中文浅色桌面，就写成“所有组合通过”。

## 运行技术检查

让 AI 在仓库根目录执行，并保留结果：

```bash
pnpm validate
pnpm test:storybook
pnpm --filter @yami/storybook build
git diff --check
```

| 命令 | 它能确认什么 |
| --- | --- |
| `pnpm validate` | 当前配置下的 lint、文档、类型、原则与生成契约、包边界及测试；不包含根脚本中的独立 Storybook 浏览器测试 |
| `pnpm test:storybook` | 执行已编写的 Storybook 与浏览器测试，包括对应 Story 的检查；没有编写的场景不等于已覆盖 |
| `pnpm --filter @yami/storybook build` | 当前 Storybook 能构建静态输出；不代表页面已部署，也不替代实际看图与操作 |
| `git diff --check` | 差异没有空白格式问题；不检查设计或业务是否正确 |

普通类型检查并不逐一覆盖所有 Story：当前 prototypes 的 TypeScript 配置排除了 `*.stories.tsx`。新增 Story 要结合 Storybook 构建、浏览器测试和实际预览验证。

只有本次真的修改 Token、组件元数据或其他生成输入时，才按相应规则运行 `pnpm generate`，检查生成差异后再验证。不要为了消除无关错误而重写生成文件、删掉断言或更新视觉基线。

## 给 AI 可复现的修正反馈

每轮只描述一组有关系的问题，并保留没有问题的部分：

```text
检查对象：本任务的 MatchaPractice Story，中文，浅色，375px。
复现：打开页面，向下滚动到“热门抹茶精选”。
实际：第二行商品标题挤压价格，截图已附。
期望：保留现有商品与排序，修正这一处窄屏布局。
限制：先定位原因，不修改其他尺寸或公共组件契约；
若必须改公共组件，先说明影响范围，等待确认。
完成后重新检查本项和受影响项，报告文件、结果与未覆盖项。
```

修复后回到同一版本记录更新结果；如果改动影响更广，应重查相关组合，而不是只截图原来出错的位置。

## 记录结果与剩余问题

```text
任务 / 负责人：
代码提交 / 未提交改动：
Story 或页面地址：
数据模式 / fixture 路径 / snapshot ID：
已检查的语言、主题、视口：
清单结果与截图：
技术检查命令、结果、未运行原因：
已知问题、影响与下一负责人：
自查状态：待检查 / 待修复 / 可评审
评审结论：待评审 / 需修改 / 已确认
发布状态：未申请 / 待授权 / 已发布并核验
```

演示行为、暂未接入的接口或没有覆盖的设备，都应写进剩余问题。不要把“能打开”“自动测试通过”“同事认可”“正式发布”合并成一个完成状态。

## 下一步

自查通过后，按[共享预览与评审](/zh/docs/review-preview)提供同事可访问的版本。获得评审结论后，再按[页面交付与发布](/zh/docs/deliver-publish)处理交付与授权；本清单不自动授予合并或发布权限。
