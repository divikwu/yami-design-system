适用于已在自己的 Fork 中完成公共能力验证的贡献者。本篇按私密上游、团队授权 Fork 的协作方式编写；仓库权限与预览权限须先由负责人实际配置，不因阅读本篇自动生效。

## 确认贡献范围

先与上游维护者确认要解决的问题、为什么能服务其他页面，以及愿意长期维护的范围。

适合贡献的内容包括：可复用组件或变体、通用交互修复、无障碍修复、清晰的使用文档，以及已去除业务耦合的页面模式。

一次活动的文案、商品数据、私有业务接口、项目路由和未验证实验，默认留在 Fork。贡献以一项稳定能力为单位，不必等整个业务项目完成，也不把整个业务分支提交给上游。

## 准备独立的贡献分支

1. 保存当前项目工作，确认没有会被覆盖的未提交内容。
2. 按[同步上游与处理冲突](/zh/docs/sync-upstream)获取已确认的上游基线，记录 commit。
3. 从该基线创建独立贡献分支或 worktree，不在混有业务修改的分支上直接发 PR。
4. 只移入这项能力需要的实现、文档、测试及对应生成文件。
5. 重新检查差异，确认没有带入相邻任务和个人环境配置。

不熟悉 Git 的同事可以让 AI 或工程同事完成操作，但需要明确说出目标仓库、基线、允许带入的文件和禁止改动的范围。

```text
请准备一个面向上游的独立贡献分支。
上游与基线：[填写仓库及 commit]
公共能力：[填写已确认范围]
来源任务：[填写项目分支或已保存版本]
只提取必要的实现、用法、示例、测试和生成文件。
业务内容、接口、路由和其他任务保持不变。
先列出拟纳入的差异，不自动推送、发 PR、合并或发布。
```

## 去除业务耦合

把真实业务数据替换为允许共享的固定示例，将接口和鉴权留在使用方，通过参数与回调表达组件所需能力。

检查组件包没有依赖应用或 prototype 层。页面模式仍由合适的页面组合层负责，不因要贡献上游就全部搬进 `packages/design-system`。

验证示例脱离原项目后仍能运行；如果需要私有环境变量或原项目专属接口，贡献范围还没有真正独立。

## 验证并说明兼容性

以贡献分支上的最终差异为准重新验证，不沿用尚未提取前的业务分支结果：

```bash
pnpm validate
pnpm test:storybook
git diff --check
```

涉及 Storybook 文档或组件目录时，再构建 Storybook 并运行 `pnpm check:docgen`。新增元数据或 Token 时先运行 `pnpm generate`，审查生成文件。

说明是否改变参数、默认值、交互、视觉尺寸或 Token 含义；即使 TypeScript 没有报错，页面仍可能发生视觉或行为变化。

涉及共享包变化时，与维护者确认 Changeset 记录及变更级别；这不是执行发布的授权。

## 提交和处理 PR

在得到提交授权后，将独立贡献分支推送到自己的 Fork，向指定上游基线发起 PR。确认 PR 的来源、目标与文件差异均正确。

PR 至少包含：问题和范围、上游基线、相关任务、前后效果、Storybook 或预览入口、验证结果、兼容性影响、迁移方式及已知限制。

评审意见继续在同一贡献范围内修改。若上游已更新，先处理差异并重新验证；不要用强制覆盖来隐藏冲突，也不要顺带合入业务项目的新功能。

由上游维护者检查设计、接口、测试、资产权限和 CI 后决定是否合并。贡献者交付的是待评审能力，不是必然获准的上游改动。

## 合并后完成收尾

- 记录上游实际合并的 commit，并将其关联到原任务。
- 让原项目按正常同步流程吸收上游版本，处理原有本地实现的重复或冲突。
- 通知其他 Fork 哪项能力可用、是否需要迁移以及如何验证。
- 区分“已经合并”与“已发布到 Storybook 或其他站点”；后者需要单独发布流程。

## 常见问题

**PR 出现大量业务文件？** 暂停提交，回到干净上游基线重新提取最小能力，不请维护者从整包业务差异中猜测要合并什么。

**别的 Fork 为什么没有立刻出现更新？** Fork 需要主动同步，并将更新合入自己的项目分支，再检查页面。

**上游暂不接收这项能力？** 保留在项目范围内，记录原因与限制；不要将其标记为已维护的公共组件。

## 下一步
