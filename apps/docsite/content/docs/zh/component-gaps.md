适用于页面创建者、设计师和组件维护者。不需要先写出新组件；这一篇的目标是让另一个人能够理解并复现你遇到的问题。

## 先准备一个具体场景

准备页面预览或截图、使用的组件名称、当前代码版本，以及希望完成的用户操作。

把问题写成行为差异，而不是直接指定解决方案：例如“窄屏下，长标题挡住了操作按钮”，比“给组件加一个自定义高度”更方便判断原因。

没有代码访问权限的同事，可以提供可访问的预览与复现步骤，由任务负责人补充版本信息。

## 检查已有能力

1. 在 [Storybook 组件目录](https://yami-design-system-storybook.vercel.app) 中查找同类组件。
2. 阅读组件的 Usage 和 Controls，确认相关参数、状态以及支持范围。
3. 用相同文案、数据和屏幕尺寸复现；不要只比较默认示例与复杂业务页面。
4. 让 AI 对照该组件的 `meta.json`、`usage.md`、Story 和公共导出，列出已经尝试的方式。

例如，`AspectRatio` 只控制宽高比例。图片裁切、加载状态与背景由使用者负责，这类需求不应直接变成它的新参数。

如果调整已有参数或组合公共组件就能解决，记录使用方法即可，不必新增能力。

## 提交可复现的反馈

将下面的信息交给团队约定的任务负责人或组件维护者；提交位置由团队指定，不假定已配置自动工单系统。

```text
页面与任务：
负责人：
组件名称及 Storybook 页面：
代码版本或 commit：
语言 / 主题 / 屏幕尺寸：
数据模式及快照标识：
复现步骤：
当前行为：
期望行为：
已经尝试的参数或组合：
影响的其他场景：
预览、截图或最小示例：
是否阻塞当前任务：
```

截图标出发生问题的区域；交互问题附上操作顺序。正式评审使用固定数据，避免商品内容变化后无法复现。

提交前移除真实用户信息、访问令牌和不必要的业务数据；仓库私密不等于所有数据都适合共享。

## 与维护者确认处理方式

| 判断 | 接下来做什么 |
| --- | --- |
| 已有能力但用法不清楚 | 修正页面调用，补充用法示例。 |
| 组件行为与现有约定不一致 | 建立失败用例，修复并检查其他使用处。 |
| 同一组件需要可复用的新表现 | 明确变体含义与默认行为，再决定扩展。 |
| 存在独立、重复出现的交互职责 | 评估新组件的边界、数据与状态。 |
| 只服务一次活动或项目 | 保留在项目页面中，不默认进入公共组件库。 |

先确认由谁处理、验收条件和对当前任务的影响，再开始改公共代码。临时方案也要标明范围、限制和后续负责人。

## 如何确认反馈有效

- 另一位同事能够按步骤得到相同结果。
- 期望行为可判断通过或失败，不只写“更美观”。
- 维护者已经给出处理方向和负责人。
- 当前任务知道继续制作、等待修复还是使用已确认的临时方案。

这份已确认的问题记录就是本篇的交付物，不是“必须新增一个组件”的承诺。

## 常见问题

**AI 已经写好了新组件，要直接合并吗？** 先对照现有组件与契约检查。能运行只说明完成了一个实现，不说明它适合成为公共能力。

**只有我的页面需要，是否不能做？** 可以在项目范围内实现；避免改写公共默认行为，并明确它不是已获维护的通用组件。

**维护者无法复现？** 补齐版本、输入数据、尺寸和操作步骤，先统一环境，再讨论视觉或行为差异。
