静态页面能够说明布局，却不能完整说明状态怎样变化。弹层从哪里进入、内容切换是否连续、操作完成后怎样反馈，都会影响原型是否接近真实产品。没有共同参考时，动效容易变成凭感觉添加的装饰。

YAMI 将 [Motion 官网示例](https://motion.dev/examples)作为动效模式与实现方法的参考库。团队先理解相近案例的运动意图、状态关系和实现方式，再选择原生 CSS、浏览器 API 或 Motion for React。参考案例不是必须照搬的规范，Motion 也不是所有效果的默认依赖。

当前仓库直接安装的专用动效库只有 `motion@13.1.0`，并在 Canvas 中通过 `motion/react` 使用。设计系统组件与原型页面仍优先采用原生能力；新的原型需求明显超出 CSS 的表达范围时，再选择 Motion 参与实现。

## 为什么需要动效参考库

参考库让团队从“做一个好看的动画”转向“选择一个能解释变化的模式”。进入、退出、布局、手势和滚动案例提供了可比较的起点，也让设计师与开发者讨论同一个运行结果。

- 找到与当前交互相近的模式，避免每次从零设计。
- 观察状态怎样衔接，而不只看最终截图。
- 对比持续时间、缓动、位移与中断行为。
- 阅读实现方式，判断原生 CSS 是否已经足够。
- 提前发现复杂效果在响应式、性能和无障碍方面的代价。

只有帮助用户理解操作结果、导航方向或内容层级的运动，才值得进入页面。

## Motion 可以提供哪些参考

[Motion for React 文档](https://motion.dev/docs/react)覆盖元素进入退出、布局动画、Hover 与 Press、滚动、拖拽、弹簧和 Motion Value。示例库还包含按钮、弹层、列表、导航、加载和页面切换等完整交互。

查找参考时应从问题出发：需要解释弹层层级，可以查看 Dialog 或 Overlay；需要说明内容重新排序，可以查看 Layout Animation；需要表现页面上下文改变，可以查看 Page Transition。不要因为案例视觉醒目，就把它放进没有相同交互目的的页面。

`initial`、`animate`、`exit` 和 `transition` 表达状态变化，`AnimatePresence` 协调退出阶段，`useReducedMotion` 响应用户偏好。即使最终选择 CSS，这些概念仍能帮助团队把动效描述清楚。

## 怎样阅读一个 Motion 案例

不要只记录“淡入”或“弹一下”。一个参考需要拆解成可实现、可评审的信息：

| 维度 | 需要回答的问题 |
| --- | --- |
| 动效目的 | 它在解释状态、方向、层级还是操作结果？ |
| 触发条件 | 点击、滚动、Hover、组件挂载还是数据变化？ |
| 变化属性 | 透明度、位移、缩放、旋转还是布局？ |
| 节奏 | 高频反馈还是低频页面变化？持续多久？ |
| 中断行为 | 动画期间再次操作会继续、反转还是重置？ |
| 最终状态 | 关闭动画后，内容是否仍然完整且可操作？ |
| 无障碍 | 减少动态效果模式需要移除什么、保留什么？ |

参考的重点是交互意图与运动关系。颜色、距离、时长和代码都要重新适配当前页面。

## 从参考案例到 YAMI 原型

一次完整的引入流程包括：

1. 明确原型中需要解释的状态变化。
2. 在 Motion 示例库中寻找一至三个相近模式。
3. 记录触发条件、变化属性、节奏、最终状态和中断行为。
4. 删除与当前任务无关的装饰性运动。
5. 判断原生 CSS 是否能够完整表达效果。
6. 使用 YAMI 的 Token、距离和节奏重新实现。
7. 同时设计减少动态效果方案。
8. 在 Storybook 或 Canvas 中检查真实操作体验。
9. 保存可复现的 Story、页面路径和评审结论。

这套流程将“找参考”和“采用依赖”分开。团队可以参考 Motion 的状态模型，但使用 CSS 完成实现。

## 什么时候使用原生实现

组件内部的高频、局部和固定状态变化默认使用原生 CSS 或浏览器 API：

- Hover、Focus、Press 的颜色与短距离位移。
- Spinner 与 Skeleton shimmer。
- ProductCard 图片在固定几何内轻微缩放。
- 横向列表和锚点的平滑滚动。
- 元素始终存在，只在少量固定样式之间切换。

常用能力包括 CSS `transition`、`@keyframes`、平滑滚动、`requestAnimationFrame` 与 `IntersectionObserver`。如果 `transition: opacity 150ms` 已经能完整表达效果，就继续使用 CSS，不必为了与参考案例采用相同技术而引入 Motion。

## 什么时候使用 Motion for React

当效果依赖 React 状态和组件生命周期，原生实现开始需要大量临时类名、计时器或清理逻辑时，再考虑 Motion：

- 需要协调挂载、进入和退出。
- 多个元素必须按同一状态同步变化。
- 动画需要中途打断、反转或重新定向。
- 手势、拖拽或布局变化与 React 状态紧密关联。
- 页面或应用外壳需要表达上下文切换。

当前 YAMI Canvas 使用 `motion` 与 `useReducedMotion` 处理控制面板进入和预览切换。这是现有直接用例，不是永久限制；新的原型可以在边界清楚、需求成立并完成验证后使用 Motion。

## 把参考效果转换为 YAMI 规则

官网案例需要重新约束后才能进入 YAMI 原型：

- 高频组件反馈使用 100–150ms。
- 弹层与下拉菜单进入或离开约 150ms。
- 页面或主要内容切换约 200–300ms。
- 方向提示只使用 4–8px 的短距离位移。
- 优先改变透明度和 Transform，避免动画宽高、字体和网格结构。
- Hover 与 Press 不放大整个组件，也不引入装饰性阴影。
- 动画不能阻挡点击、输入、滚动或键盘焦点。

这些范围用于保持一致性，不是把所有效果压成同一种运动。

## 减少动态效果必须同时设计

[Motion 的无障碍指南](https://motion.dev/docs/react-accessibility)建议响应 reduced-motion 设置。每次选择参考案例时，都要同时确定哪些运动可以移除、哪些信息必须保留。

| 正常模式 | 减少动态效果模式 |
| --- | --- |
| 位移并淡入 | 直接显示，或仅保留短暂淡入 |
| 弹簧缩放 | 使用颜色或透明度确认状态 |
| 自动滚动或播放 | 停止并交给用户主动控制 |
| 循环装饰动画 | 停止 |
| 必要加载反馈 | 保留状态，但减少不必要移动 |

在 CSS 中使用 `prefers-reduced-motion`；在 Motion 中使用 [`useReducedMotion`](https://motion.dev/docs/react-use-reduced-motion)。减少动态效果是与正常模式同时定义的另一条实现路径。

## 一个参考案例怎样进入原型

假设原型需要让内容面板出现。团队先查看相近的面板或弹层案例，判断运动目的是说明层级和进入方向，而不是吸引注意力。收敛后只保留透明度和 8px 位移。

面板始终存在且只有一次简单状态切换时，可以使用 CSS Transition；如果需要挂载、保留退出阶段，并能在快速操作中反转，则使用 Motion：

```tsx
import { motion, useReducedMotion } from "motion/react";

export function PreviewPanel() {
  const reduced = useReducedMotion();
  return (
    <motion.aside
      initial={{ opacity: 0, x: reduced ? 0 : -8 }}
      animate={{ opacity: 1, x: 0 }}
      transition={{ duration: reduced ? 0 : 0.18 }}
    />
  );
}
```

正常模式保留方向提示；减少动态效果模式移除位移并直接进入最终状态。

## 怎样验证原型动效

1. 确认运动确实帮助理解状态、方向或层级。
2. 分别测试正常与 reduced-motion 模式。
3. 连续快速操作，检查动画能否正确中断和收敛。
4. 确认最终内容、布局和焦点在两种模式中一致。
5. 检查动画不会阻挡点击、输入和滚动。
6. 在移动端、桌面端和低性能设备上观察流畅度。
7. 在 Storybook 保存组件状态，在 Canvas 验证页面上下文。
8. 记录时长、变化属性、触发条件、已测范围和已知限制。

自动化测试可以验证状态分支，但动效是否帮助理解变化仍需要真实操作与视觉评审。

## 常见误区

- 直接复制官网代码，却没有说明动效解决什么问题。
- 为简单 Hover 或颜色变化引入 Motion。
- 只模仿视觉效果，不处理挂载、退出与中断状态。
- 在相邻组件中使用互不相关的时长和缓动。
- 让弹簧、缩放或视差出现在所有页面。
- 只把持续时间设为零，却留下初始状态闪烁。
- 让动画过程决定页面高度、焦点或必要信息是否存在。
- 把参考案例当作设计规范，而不适配内容、设备和品牌边界。

## 让参考服务于真实体验

Motion 是 YAMI 的动效参考库和可选实现工具。团队借助官网案例理解动效模式，再根据原型需求选择原生 CSS、浏览器 API 或 Motion for React，以最轻、最清楚和最容易验证的方式完成真实交互。

最终目标不是让原型“动得更多”，而是让状态变化更容易理解，让实现可以复现，并让不需要运动的用户获得同样完整的体验。
