从 Figma 交付一个组件，最容易被误解为“把视觉还原成代码”。视觉一致当然重要，但生产组件还要回答属性如何组合、状态如何表达、键盘如何操作、主题如何切换，以及调用方如何知道它已经可以使用。

YAMI 把这个过程视为一条证据链。截图是其中一项输入，不是最终契约。

## 从行为和边界开始

实现前先明确组件负责什么、不负责什么。页面结构、业务数据和路由通常属于应用；交互状态、可访问性和 Token 绑定属于组件。

然后检查 Catalog 与 Storybook。已有组件能够满足任务时，优先复用公共 API。若存在真实缺口，先定义最小属性和状态，而不是复制源码后局部修改。

这一阶段需要记录：

- 必需与可选属性。
- 默认、hover、pressed、focus、disabled 和错误状态。
- 中文、英文和长文本表现。
- 亮暗与 inverse 表面的映射。
- 窄屏和宽屏中的结构变化。

## 让 Token 承担视觉决定

Figma 中的颜色、间距、圆角和排版必须映射到现有语义 Token。找不到对应值时，不应该直接写最接近的 CSS；需要先判断设计稿是否偏离规范，或系统是否真的缺少一个可复用语义。

品牌红与操作红尤其不能通过吸色混用。Card 不添加装饰边框和阴影，焦点使用统一外轮廓，禁用态不能通过整体 opacity 生成。

这些约束让同一个组件可以自动响应主题与语言，而不是把每个 Figma 画板固化成独立分支。

## Storybook 是可操作规格

Storybook 不只展示“默认看起来怎样”。它需要覆盖关键属性、状态、边界内容和交互步骤，让设计师与开发者在同一个运行结果上评审。

每个组件还需要元数据与使用说明。生成 Catalog 记录名称、成熟度和公开导出；Registry 记录交付依赖。只有这些来源保持一致，组件才可以被其他应用和 Agent 可靠发现。

## 验证不止一个截图

一个可验证组件至少经过四层检查：

1. 静态层：类型、lint、公共边界和 Token 合法性。
2. 交互层：键盘、焦点、状态切换和事件结果。
3. 视觉层：中英、亮暗与目标断点的真实渲染。
4. 集成层：在页面组合中确认内容顺序和业务上下文。

视觉对比应该检查结构、对象数量、文案、几何与关键状态。像素差异可以帮助定位问题，但不能证明交互正确；HTTP 200 也不能证明浏览器完成渲染。

## Agent 如何参与

Agent 可以快速读取组件文档、检索 Token、搭建测试和收集证据。它必须使用 YAMI Skill 的读取顺序，限制改动范围，并明确区分来源事实、实现观察和待验证假设。

当设计与代码来源冲突时，Agent 应暴露冲突，而不是静默选择一侧。品牌资产权限、组件成熟度和生产发布也不能由 Agent 自行推断。

从 Figma 到代码的真正终点不是“看起来像”，而是设计意图已经进入公共契约，并且下一位协作者可以重复验证。
